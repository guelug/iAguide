## Un turno, cinco verbos

Todo arnés serio — Hermes Agent, OpenClaw, el chat que escribiste un sábado — hace el mismo baile:

1. **Intake** del mensaje (y quizá una interrupción en cola).
2. **Armar** contexto: política de sistema, skills, memoria, turnos recientes.
3. **Llamar al modelo** (completions, Messages nativo, Responses o un runtime embebido).
4. **Ejecutar herramientas** si el modelo las pidió; repetir hasta texto o presupuesto.
5. **Persistir** el transcript y volcar memoria durable.

El modelo se cambia. El bucle es el producto.

<VisualSlot caption="Recorre los cinco verbos de un turno. El pulso es trabajo moviéndose por el arnés, no un segundo cerebro." />


Los cinco verbos son el mapa iAguide. El curso de Hugging Face nombra el mismo pulso por dentro: Thought, Action, Observation, en un `while` hasta que el objetivo está cumplido. No son dos bucles. El while del curso **es** el paso 4 (y un trozo del 3). Intake, armar y persistir los pone el arnés alrededor.

## Thought, Action, Observation: el while

Un agente, en la Unidad 1, es un sistema que usa un modelo de lenguaje para interactuar con un entorno y alcanzar un objetivo. El modelo razona. El <Term id="harness">arnés</Term> ejecuta. El ciclo:

1. **Thought** — el modelo decide el siguiente paso. Plan, análisis, un rechazo, una autocorrección. Texto.
2. **Action** — el modelo emite una petición estructurada: qué herramienta, con qué argumentos. Sigue siendo texto.
3. **Observation** — el entorno responde. Un cuerpo de API, un error, un número. El arnés **añade** esa cadena. No se muestrea.

En analogía de programación: un `while`. Sigue hasta el objetivo, o hasta un presupuesto de pasos. Los frameworks meten las reglas en el <Term id="system-prompt">system prompt</Term>. El dummy las deja a la vista. El parseo de veinte líneas vive en [agente dummy](/es/m/dummy-agent): esta lección no lo reescribe.

El curso lista tipos de Thought que caben en ese párrafo: planear, analizar, decidir, resolver, integrar memoria del hilo, auto-corregirse, fijar un objetivo, priorizar. Siguen siendo tokens. Un «plan en tres pasos» no es un planner aparte; es prosa que el siguiente Action puede cumplir o ignorar. Si ignoras el parseo, el plan es teatro.


<Callout>
La Observation no es el siguiente Thought «más honesto». Es un log del entorno. Si el modelo la escribe, tienes una alucinación con formato de meteorología. Si tú la escribes después de ejecutar, tienes un agente.
</Callout>

## Alfred y el tiempo en Nueva York

El curso trabaja el ciclo con Alfred. Un usuario pregunta el tiempo en Nueva York. Alfred no lo tiene en los pesos. Tiene `get_weather`.

**Thought.** «El usuario necesita el tiempo actual. Hay una tool. Primero la llamo.»

**Action.** Una petición estructurada, no prosa suelta. En el dummy es un blob JSON; aquí, en voz de aula, sin literales que rompan el MDX:

    Thought: I need to check the current weather for New York.
    Action:
      action = get_weather
      action_input location = New York

**Observation.** El arnés ejecuta, recibe algo como: «Current weather in New York: partly cloudy, 15 °C, 60% humidity.» Esa cadena se **añade** al prompt. No la genera el decoder.

**Thought otra vez.** «Ya tengo los datos. Puedo contestar.»

**Final.** `Final Answer:` con el tiempo. El bucle cierra porque el objetivo está cumplido, no porque el modelo se haya cansado.

Si la Observation hubiera sido un error de API, Alfred reentra: otro Thought, quizá la misma tool con otro argumento, quizá un fallback. Eso es adaptación. No es un segundo cerebro. Es el while con evidencia nueva en la ventana.

Cómo se **añade** la Observation, en el orden del curso: parsear la Action (nombre y argumentos), ejecutar el callable, concatenar el resultado. Tres pasos. Si saltas el primero, ejecutas basura. Si saltas el segundo, el modelo se observa a sí mismo. Si saltas el tercero, el siguiente generate no ha visto el mundo.

Las Observations pueden ser un error HTTP, un cambio en un fichero, un número de calculadora, un timeout. El curso las llama logs de la tool. Trátalas como logs: textuales, completas, fuente de verdad *porque tú las pegaste*.


## ReAct frente a Chain-of-Thought

**Chain-of-thought** es un truco de prompting: «vamos paso a paso», para trabajo que se queda **dentro** del modelo (mates, lógica). No hay tools. Si el hecho no está en los pesos, CoT lo inventa con fluidez.

**ReAct** entrelaza Thought, Action y Observation. El modelo sale del prompt, el arnés ejecuta, vuelve evidencia. Sirve para el tiempo, la búsqueda, cualquier verdad que viva fuera de la ventana.

<Compare a="Chain-of-thought" b="ReAct">
<Side>
Lógica paso a paso, sin herramientas. El modelo se habla a sí mismo y luego responde. Sirve para aritmética y puzzles cerrados. Fuera de los pesos, alucina con estilo.
</Side>
<Side>
Lógica paso a paso más Actions y Observations. El modelo puede ir a buscar. Sigue haciendo falta stop-and-parse, o ReAct se derrumba otra vez en CoT con una observación falsa.
</Side>
</Compare>

Los modelos de razonamiento recientes (el curso nombra DeepSeek-R1 y la familia o1) entrenan una separación think-then-answer con tokens especiales. Eso es **entrenamiento**, no un prompt. No lo confundas con el while dummy. El dummy es un prompt más una secuencia de stop más tu Python.

## El Thought es opcional en function-calling

El curso lo dice en Thoughts y lo retoma en Actions: si el modelo se afinó para function-calling, el monólogo visible **puede omitirse**. Su «pensamiento» está en los pesos y en un mensaje de tool, no en un párrafo Thought:. El dummy sigue pidiendo Thought: porque induce el ciclo a un chat genérico, no a un especialista entrenado.

Esa distinción es toda la lección de [fine-tuning para function calling](/es/m/function-calling-ft). Aquí basta: no exijas un monólogo a un modelo que ya emite tool_calls. Exige el while, el parseo y la Observation honesta.

Forma del hueco dummy, en prosa de aula — el código con literales está en [dummy-agent](/es/m/dummy-agent):

    output = client.chat.completions.create(messages, max_tokens=150, stop=Observation:)
    text = output.choices[0].message.content
    # parsear Action, ejecutar get_weather tú
    observation = get_weather(location)
    # concatenar Observation: + el resultado real
    # muestrear otra vez hasta Final Answer:

`stop=Observation:` no es adorno. Sin él, el modelo escribe la Observation. Con él, y sin runTool, tienes un cuelgue. Los dos bugs parecen agentes en una demo. Ninguno lo es.


## Interrupción, presupuesto, fallback

Alrededor del while, el arnés pone tres ideas que el curso de Unidad 1 apenas nombra y que un producto sí necesita:

- **Interrumpible** — una llamada HTTP o un lote de tools se puede abandonar con /stop o un mensaje nuevo. El texto parcial no debe ensuciar el transcript.
- **Presupuesto** — techo de iteraciones o de reloj para que un bucle no queme un fin de semana de tokens. El curso habla de «hasta que el objetivo esté cumplido»; tú pones el tope.
- **Fallback** — si el proveedor primario falla (429, 5xx, auth), prueba una cadena. Los subagentes a menudo **no** heredan esa cadena.

<Compare a="Chat" b="Bucle de arnés">
<Side>
Mandar mensaje → imprimir respuesta. Sin rondas de tools, sin modelo de interrupción, sin claim de escritura durable.

</Side>
<Side>
Serializar por sesión, armar un prefijo estable, ejecutar tools con permisos, compactar cuando la ventana se llena, entregar por un adaptador.

</Side>
</Compare>

El pulso que pinta el diagrama no es «el modelo pensando más». Es trabajo moviéndose: intake → assemble → generate → tools → persist. Si una flecha se atasca, no subas la temperatura. Mira el verbo.


Los cinco verbos no son un framework. Son la lista contra la que testear el tuyo. El while de Alfred cabe en una hoja. El producto es no mentir en ninguna flecha.


## Hermes frente a OpenClaw

Hermes concentra el bucle en `AIAgent` (`run_agent.py`) para CLI, gateway, ACP, cron y librería. OpenClaw posee un **Gateway**: el RPC `agent` acepta al momento y un run embebido emite eventos `assistant` / `tool` / `lifecycle`. Mismos cinco verbos; distinto dueño del proceso. Mapas oficiales: [bucle Hermes](https://hermes-agent.nousresearch.com/docs/developer-guide/agent-loop), [bucle OpenClaw](https://docs.openclaw.ai/concepts/agent-loop).

No elijas por el diagrama de marketing. Elige por quién serializa la sesión y quién aborta un generate a mitad de stream. El while de Alfred cabe en los dos; el Telegram de más abajo solo falla si el persistido es mentiroso.

## Caso — la media respuesta interrumpida

**Caso.** Un usuario de Telegram manda otro mensaje a mitad de stream. El arnés interrumpe pero también guarda el fragmento del asistente como turno cerrado. Siguiente llamada: dos mensajes assistant seguidos → 400 del proveedor.

**Patrón de arreglo.** Al interrumpir: abandonar el hilo HTTP, no commitir contenido parcial, encolar o dirigir el texto nuevo, mantener alternancia válida. Eso es el verbo persistir con disciplina, no un modelo «más obediente».

El mismo bug aparece si abortas un tool call a medias y dejas una Action sin Observation. El siguiente Thought lee un rito roto. Cierra el turno o no lo escribas. No dejes un fantasma.

## El bucle se testea sin GPU

Tres tests que no necesitan un modelo real:

1. **State machine** — given estado X y evento Y, el siguiente estado es Z. Tests del bucle puro.
2. **Tool dispatch** — el handler se llama con los argumentos correctos. Fixtures con mocks.
3. **Interrupt** — un cancel llega a mitad de tool. El bucle abandona y persiste el cancel.

Estos tests corren en milisegundos. Sin API key. Son el grueso de tu cobertura.
