## Un chat no es un arnés

Un chat manda mensajes a un modelo e imprime la respuesta. Un <Term id="harness">arnés</Term> es un **bucle**:

usuario → <Term id="thread">hilo</Term> → prefill / decode → quizá <Term id="tool">herramientas</Term> → quizá un <Term id="subagent">subagente</Term> → acierto o fallo de caché → <Term id="compaction">compactación</Term> → de vuelta al usuario.

El modelo es un motor de tokens dentro de ese bucle. Cambias el motor; el bucle sigue. Eso es todo este módulo.

## Prefill y decode: la base del arnés

Dentro del paso "modelo" del bucle, hay dos fases muy distintas que importan para diseñar el arnés:

- **<Term id="prefill">Prefill</Term>** — el prompt y el historial de mensajes cacheado se procesan **en paralelo** por cada capa. La KV cache para esos tokens se construye una vez. Está limitada por throughput (compute-heavy), es amigable con la GPU, y se amortigua sobre todos los tokens del prefijo. Un system prompt de 12k pagado en cada turno es la línea más común de tu factura de inferencia.
- **<Term id="decode">Decode</Term>** — cada token nuevo se genera **secuencialmente**, atendiendo a la KV de cada token previo. Está limitada por latencia (memory-bandwidth-heavy), y el coste de cada token crece con la longitud del prefijo.

Las dos fases son la razón por la que "system prompt corto" y "respuesta concisa" son objetivos de optimización distintos en el arnés. El primero se amortigua sobre todos los turnos futuros si mantienes el prefijo estable; el segundo solo importa una vez por turno. Inflar el prefijo con mil tokens de skills obsoleto cuesta prefill para siempre. Inflar la respuesta con dos frases de cortesía cuesta decode una vez.

<Callout>
Cuando optimizas el arnés, decide cuál de las dos fases estás optimizando. Si el problema es el primer token lento, el prefill es largo. Si el problema es la respuesta lenta, el decode es largo. Si el problema es la factura, probablemente prefill fresco que debería ser cacheado. Distintas palancas.
</Callout>

## A3B / MoE en el arnés

Un modelo **48B-A3B** (Mixture-of-Experts) tiene 48B parámetros en disco y ~3B **activos por token**. Esto cambia la economía del arnés en dos sitios:

- **Memoria** dominada por los totales (48B en Q4 ≈ 24 GB en disco). Cargar el modelo cuesta 48B-veces-bytes en RAM unificada o VRAM.
- **FLOPs** por token dominados por los activos (3B). El coste por token está más cerca del de un denso 3B que del de un denso 48B.

Para el arnés, esto significa tres cosas prácticas:

1. **El coste de prefill escala con FLOPs activos, no con totales** — un prefill de 12k tokens en un 48B-A3B paga como un denso 3B, no como un denso 48B. Eso abarata el contexto largo.
2. **La atención sobre la KV sigue siendo densa** — el FFN disperso abarata el cómputo; la atención no. Hacer el contexto más largo sigue siendo caro en atención.
3. **El coste de memoria no baja** — los 48B totales siguen siendo 48B en disco. La caché de modelos en RAM/VRAM cuesta lo mismo.

## Perfiles y el system prompt

Un <Term id="system-prompt">perfil / system prompt</Term> es el texto permanente: quién es el agente, qué no debe hacer, qué herramientas hay, cómo formatear. Se inyecta cada turno o se sostiene en una <Term id="prompt-cache">caché de prefijo</Term>. No es "memoria de este usuario". Es política.

Los buenos perfiles son cortos, comprobables y versionados. Un manifiesto de 20k tokens cuesta prefill en cada prefijo nuevo y aun así se ignora cuando el hilo es ruidoso.

## Herramientas

Una herramienta es una función que el modelo puede *pedir*: un nombre, un esquema JSON de argumentos y código que **tú** ejecutas. El modelo no tiene bash por arte de magia. El arnés parsea un <Term id="tool-call">tool_call</Term>, mira <Term id="permissions">permisos</Term>, ejecuta y añade un mensaje de resultado.

Si omites permisos, construiste un control remoto para quien hable con el modelo.

## Hilos, no corazonadas

Un hilo es la unidad durable: mensajes, resultados, a veces un directorio de trabajo. No es una cookie de <Term id="session">sesión</Term>. Diseña como si "este hilo fuera el contexto" y admite que lo vas a compactar.

## Subagentes

Un subagente es un bucle anidado: menos herramientas, prompt más estrecho, casi siempre un contexto nuevo o recortado, devuelve un resumen. El aislamiento es la virtud (un glob salvaje no inunda al padre). El coste es el impuesto (otro prefill, otra caché). Úsalos cuando el padre se ahogaría en bruto, no como pack de personalidad.

## Ahorrar tokens a propósito

Tres tácticas honestas:

1. **Caché de prefijo / prompt** — deja el prefijo largo e idéntico para reutilizar trabajo entre turnos.
2. **Recuperar frente a empujar** — no pegues el wiki. Trae la página que hace falta.
3. **Compactación** — resume turnos viejos antes de que la ventana reviente. Es con pérdida; registra lo que tiras.

## Kernel significa dos cosas

En GPU, un <Term id="kernel">kernel</Term> es el programa compilado que corre en el dispositivo (atención, matmul). En arneses, la gente dice "kernel" al runtime interno: el que hace stream, llama herramientas y decide parar. Misma palabra. Capa distinta. Si alguien dice "el kernel ha petado", pregunta cuál.

## Un bucle trabajado

1. El mensaje de usuario aterriza en un hilo.
2. El arnés arma mensajes: perfil, historia compactada, texto nuevo, esquemas de herramientas.
3. **Prefill** del prefijo (acierto de caché si el prefijo coincidió byte a byte).
4. **Decode** hasta un stop o un tool call.
5. Si hay tool call: permisos → ejecutar → añadir resultado → ir a 3.
6. Si nace un subagente: corre 1–5 en un hijo, añade un resumen, sigue.
7. Si la ventana aprieta: compacta y sigue.
8. Stream de la respuesta visible. Persistir el hilo.

## El arnés y la elección del modelo

El arnés es el mismo independientemente del modelo. Pero el modelo **sí** cambia la economía del arnés:

- **Dense 7B** — barato en memoria, caro por FLOPs por token. Un prefill largo cuesta.
- **Dense 70B** — caro en memoria (140 GB en FP16), menos por token. Cabe en hardware de servidor.
- **48B-A3B** — MoE barato en FLOPs, caro en memoria. Cabe en hardware de servidor con cuantización. Prefill barato por FLOPs pero atención densa.
- **Mixtral 8x7B** — MoE similar al A3B pero con otra distribución de expertos.

Tu arnés **no debería** saber cuál es. Pero tu `model_card.json` o equivalente debería decir "MoE 48B-A3B" para que tu dashboard de prefill pueda estimar FLOPs activos y no totales.

<Myth>
"Un modelo más grande siempre es mejor." No para el arnés. Un 7B denso en un arnés con caché de prompt perfecta puede costar menos por turno que un 70B denso con caché rota. La elección de modelo es ortogonal a la optimización del arnés.
</Myth>

## El arnés en producción: tres señales

Un arnés en producción tiene tres señales operativas:

1. **Tasa de acierto de caché de prefijo** — debería estar > 80% en operación normal. Si cae, casi seguro mutaste el prefijo sin querer.
2. **Coste por turno** — input + output + tools. Si sube sin un cambio de modelo, el prefill está re-pagándose.
3. **Latencia del primer token** — proxy del prefill. Si sube, el contexto creció.

Las tres señales son ortogonales. Una puede subir mientras las otras dos bajan. Por eso el dashboard tiene tres paneles, no uno.

## Por qué el arnés se queda, el modelo cambia

El modelo es commodity. El arnés es producto.

- **Modelo commodity** — el mismo MoE 48B-A3B lo hospedan tres vendors con precios distintos. Cambias de vendor en una config.
- **Arnés producto** — el bucle, las tools, los permisos, los skills, el gateway, los jobs — todo eso es código tuyo. Cambiarlo cuesta semanas.

Si tu arnés está bien abstraído (un solo punto que conoce al modelo, todo lo demás unaware), cambias de modelo en un día. Si tu arnés tiene "este prompt solo funciona con Claude 3.5" hardcodeado, cambias de modelo en un trimestre.

## El arnés mínimo, en cinco líneas

```python
def turn(thread, user_text):
    thread.append(user_message(user_text))
    while True:
        prompt = assemble_prompt(thread, profile=PROFILE, tools=TOOLS)
        out = model.generate(prompt)
        if not out.tool_call:
            thread.append(out.assistant_message)
            return out.text
        thread.append(out.tool_call_message)
        result = dispatch(out.tool_call, policy=POLICY)
        thread.append(tool_result_message(out.tool_call.id, result))
```

Cinco líneas. El resto es detalle (compactación, retries, persistencia). Si puedes testear esto sin un modelo, tienes el esqueleto.

## Lo que el arnés NO es

- **No es el modelo** — el modelo es el motor; el arnés es el vehículo.
- **No es el framework** — el framework (smolagents, LangGraph, LlamaIndex) es un dialecto; el arnés es la idea.
- **No es la plataforma** — Telegram, Discord, Slack son adaptadores; el arnés es el bucle detrás.
- **No es el system prompt** — el system prompt es input del bucle, no el bucle mismo.

Confundir estas cosas es depurar la capa equivocada. Caso clásico: "Hermes ignora las tools" — el modelo está bien; el arnés no las expone.

## Caso — Hermes-el-nombre frente a Hermes-el-bucle

Un equipo abrió "Hermes ignora las tools" contra pesos de Nous. El perfil no listaba tools; el runtime no parseaba llamadas. Depuraban el motor. El arnés — esta página — estaba vacío. Quédate con el mito del principio cuando alguien diga "Hermess."

## Caso — la KV cache que se quedó sin memoria

Una sesión larga con un denso 70B mantuvo la KV cache del prefill en RAM. La ventana creció a 100k tokens; la KV cache pasó de 4 GB a 40 GB. El contenedor OOM-killed antes de terminar la compactación. La fix fue: topes duros por ventana + compactación proactiva antes del 50%.
