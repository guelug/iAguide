## A turn is a trace

*Named source: Hugging Face Agents Course, Bonus Unit 2, [AI Agent Observability and Evaluation](https://huggingface.co/learn/agents-course/bonus-unit2/what-is-agent-observability-and-evaluation) and [introduction](https://huggingface.co/learn/agents-course/bonus-unit2/introduction) (Burtenshaw, Thomas, Simonini, & Paniego, Apache-2.0).*

Without observability, an agent is a black box that sometimes emails the customer. **Traces** are one user task end to end. **Spans** are the steps inside: prefill, decode, tool call, subagent, retrieve. OpenTelemetry is the usual wire. Langfuse, Arize, Phoenix are dashboards that speak it. smolagents can instrument with the OpenTelemetry path the docs name (`SmolagentsInstrumentor` in the library docs at https://huggingface.co/docs/smolagents). Check the tool’s docs for what is actually supported that week.

## Why it matters

*Named source: Hugging Face Agents Course, Bonus Unit 2, [what-is-agent-observability-and-evaluation](https://huggingface.co/learn/agents-course/bonus-unit2/what-is-agent-observability-and-evaluation).*

The unit lists: understand cost versus accuracy; measure latency; detect harmful language and prompt injection; monitor user feedback. In their words, it makes a demo agent ready for production. iAguide adds: you cannot alert on a span you never named. The dummy loop’s stop-and-parse is still the inner clock; observability is how you see it after deploy.

Practical tip: name spans after harness steps you already teach: apply_template, model.generate, tool.search, tool.ticket_update, compact. If you cannot point at the dummy `while`, you will log “LLM” as one blob and learn nothing.

## Tools, not a religion

*Named source: same Bonus Unit 2 page (Observability Tools); OpenTelemetry https://opentelemetry.io/docs/; Langfuse https://langfuse.com; Arize https://www.arize.com

Some tools are open source with large communities. Some specialise (observability, evals, prompt management); some cover the whole LLMOps workflow. The course tells you to read docs and pick. Many agent frameworks expose metadata via OpenTelemetry; vendors also ship custom instrumentations because the field moves fast. Do not invent a Phoenix API here if the unit did not print it. Phoenix is named in this particularity’s original stub as a sibling dashboard; confirm against current vendor docs before you copy method names.

Practical tip: one exporter in staging first. Two vendors on day one is two incomplete traces.

## Metrics the unit actually names

*Named source: Hugging Face Agents Course, Bonus Unit 2, key metrics section of [what-is-agent-observability-and-evaluation](https://huggingface.co/learn/agents-course/bonus-unit2/what-is-agent-observability-and-evaluation).*

**Latency.** Task and step. Long waits hurt. Trace both. An agent that spends 20 seconds on model calls might need a faster model or parallel calls — that example is the unit’s.

**Costs.** Per run: tokens and external APIs. Frequent tools or many prompts raise the bill. Five LLM calls for a marginal gain may not be justified. Watch for bug loops.

**Request errors.** Failed APIs or tool calls. Fallbacks and retries: if provider A is down, switch to B — again the unit’s example.

**User feedback.** Explicit: thumbs, stars, comments. Consistent negatives should alert.

**Implicit feedback.** Rephrasing, repeated queries, retry clicks. Same question twice is a signal.

**Accuracy.** You define success: correctness, retrieval accuracy, satisfaction. Mark traces succeeded or failed.

**Automated evaluation.** An LLM judge; libraries such as [RAGAS](https://docs.ragas.io/) for RAG and [LLM Guard](https://llm-guard.com/) for harm and injection, as named on the page.

Practical tip: alert on tool error ratio, not only p95 latency. SignalOps below is that sentence as a case.

A combination of these metrics is what the unit recommends. One green chart is how SignalOps shipped a 40 percent tool-error rate.

## Offline evaluation first

*Named source: Hugging Face Agents Course, Bonus Unit 2, Evaluating AI Agents / Offline Evaluation.*

Offline: controlled set, known expected outputs, often CI. Example: a math agent on [GSM8K](https://huggingface.co/datasets/gsm8k). Repeatable accuracy. The challenge is keeping the set representative. Mix small smoke tests and larger sets. Start here before deploy — the unit calls it the minimum step.

Practical tip: every production incident becomes a row. That is the loop the unit describes later. A frozen 100-item set from launch week is a trophy, not a test.

## Online evaluation second

*Named source: Hugging Face Agents Course, Bonus Unit 2, Online Evaluation.*

Online: live traffic. Success rates, satisfaction, drift, unexpected queries. Implicit and explicit feedback; maybe shadow or A/B. Harder to label. Together with offline: the unit’s loop is offline eval, deploy, monitor, collect new failures, add them to the offline set, iterate.

Practical tip: do not A/B a prompt and a model and a tool list in one shot. One change per experiment or you will not know which span moved.

## Case — SignalOps’ calm latency

*Pedagogical case in iAguide voice; metrics from Bonus Unit 2 (latency versus request errors).*

SignalOps’ p95 was 1.8s — green. Tool error rate was 40 percent (CRM timeout). The model apologised quickly, so latency looked fine. They alerted on p95 alone. A span error ratio would have paged them on day one. They added error-ratio alerts, an offline set of CRM-timeout traces, and a fallback provider as the unit suggests when provider A is down.

## Practical checklist

*Named source: Bonus Unit 2 pages under Sources; OpenTelemetry https://opentelemetry.io/docs/

1. One trace per user turn. Spans for model and each tool.
2. Alerts: latency, cost, error ratio, not only p95.
3. Offline set with ground truth before deploy.
4. Online: explicit plus implicit feedback.
5. New failures return to the offline set.
6. Injection and harm checks use named libraries from the unit, not a guessed API.

## Observability is signals; evaluation is the verdict

*Named source: Hugging Face Agents Course, Bonus Unit 2, Evaluating AI Agents section of [what-is-agent-observability-and-evaluation](https://huggingface.co/learn/agents-course/bonus-unit2/what-is-agent-observability-and-evaluation).*

The unit is careful: observability is looking at logs, metrics, and traces so the agent is not a black box. Evaluation is analysing that data (and running tests) to decide how well the agent is doing and how to improve it. Agents are non-deterministic and they drift. Without evaluation you would not know if the “smart agent” still does the job.

Practical tip: keep the two words in the runbook. “We have Langfuse” is observability. “We fail the GSM8K smoke set in CI” is evaluation. SignalOps had the first and called it the second.

*Named source: Hugging Face Agents Course, Bonus Unit 2, Latency and Request Errors in [what-is-agent-observability-and-evaluation](https://huggingface.co/learn/agents-course/bonus-unit2/what-is-agent-observability-and-evaluation).*

## Cost loops and five LLM calls

*Named source: Hugging Face Agents Course, Bonus Unit 2, Costs in [what-is-agent-observability-and-evaluation](https://huggingface.co/learn/agents-course/bonus-unit2/what-is-agent-observability-and-evaluation).*

Agents bill per token and per external API. Frequent tools or many prompts raise the bill. The unit’s example: five LLM calls for a marginal quality gain may not be justified; maybe fewer calls or a cheaper model. Real-time monitoring catches bug loops that hammer an API.

Practical tip: cap steps in the dummy `while` and log the cap as a span attribute. A cost spike with a step-budget hit is a loop, not “the model got smarter.”

## Feedback is two channels

*Named source: Hugging Face Agents Course, Bonus Unit 2, User Feedback and Implicit User Feedback in [what-is-agent-observability-and-evaluation](https://huggingface.co/learn/agents-course/bonus-unit2/what-is-agent-observability-and-evaluation).*

Explicit: thumbs, stars, comments. Consistent negatives should alert. Implicit: rephrasing, repeated queries, retry clicks. The same question twice is a sign the agent is not working. Online evaluation often has weak labels; that is why the unit pairs it with offline ground truth.

Practical tip: store the thumbs on the trace id, not in a spreadsheet. A 👍 on a hallucinated CRM update is a false positive you will only catch if the tool span is also labelled.

## Accuracy you define, judges you name

*Named source: Hugging Face Agents Course, Bonus Unit 2, Accuracy and Automated Evaluation Metrics in [what-is-agent-observability-and-evaluation](https://huggingface.co/learn/agents-course/bonus-unit2/what-is-agent-observability-and-evaluation).*

Success varies: correctness, retrieval accuracy, satisfaction. Define it. Mark traces succeeded or failed. Automated evals: an LLM judge; [RAGAS](https://docs.ragas.io/) for RAG agents; [LLM Guard](https://llm-guard.com/) for harmful language and prompt injection. The page names those libraries. Do not invent a third scoring SDK here.

Practical tip: a judge without a rubric is another black box. Write three bullets of “succeeded” before you call an LLM-as-a-judge. For RAG, steal the named RAGAS path; for injection, steal LLM Guard. Confirm current APIs in their docs.

## Smoke tests and larger sets

*Named source: Hugging Face Agents Course, Bonus Unit 2, Offline Evaluation in [what-is-agent-observability-and-evaluation](https://huggingface.co/learn/agents-course/bonus-unit2/what-is-agent-observability-and-evaluation).*

The unit wants a mix: small smoke tests for quick checks, larger sets for broader metrics. The challenge is keeping the set representative. Update it with new edge cases from production. GSM8K is their math-agent example, not a universal exam. A support agent needs CRM-timeout traces, not grade-school word problems.

Practical tip: ten golden turns in CI, one hundred in a nightly job, and every production incident as a candidate row. That is the combination the unit describes; the numbers are classroom, not a secret quota.
