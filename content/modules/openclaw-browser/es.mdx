## Un browser solo para el agente

La fuente primaria es [*Browser*](https://docs.openclaw.ai/tools/browser) de OpenClaw (s. f.). OpenClaw puede correr un **perfil dedicado de Chrome/Brave/Edge/Chromium** que el agente controla. Corre a través de un servicio local pequeño de control dentro del Gateway (solo loopback) y está aislado de tu browser personal.

Piensenlo como un **browser separado, solo del agente**. El perfil `openclaw` nunca toca tu perfil personal. El perfil builtin `user` se adjunta a tu sesión real de Chrome vía Chrome DevTools MCP. El perfil `chrome` conduce Chrome con sesión iniciada a través de la extension OpenClaw, que funciona desde el telefono sin nadie en el escritorio (OpenClaw, *Browser*, s. f.).

La lección genérica [tools](/es/m/tools) permanece agnóstica del harness. Esta es el browser gestionado de OpenClaw.

## Perfiles: openclaw, user, chrome

- `openclaw`: browser gestionado, aislado (sin extension). Default. Acento naranja por defecto.
- `user`: attach Chrome DevTools MCP a tu **Chrome real con sesión**. Chrome muestra un prompt bloqueante "Allow remote debugging?" la primera vez, así que alguien debe estar en el computador.
- `chrome`: perfil de extension para la misma sesión iniciada. Sin prompt de remote-debugging. Prefieran este cuando el usuario esta **ausente** (Telegram, WhatsApp).

Para llamadas de la tool browser del agente, el default es el browser aislado `openclaw`. Prefieran `profile="chrome"` cuando importan sesiones logueadas y el usuario esta ausente. Prefieran `profile="user"` cuando importan sesiones logueadas y el usuario está en el computador para aprobar el attach. Pongan `browser.defaultProfile: "openclaw"` si quieren modo gestionado por defecto (OpenClaw, *Browser*, s. f.).

```bash
openclaw browser --browser-profile openclaw doctor
openclaw browser --browser-profile openclaw status
openclaw browser --browser-profile openclaw start
openclaw browser --browser-profile openclaw open https://example.com
openclaw browser --browser-profile openclaw snapshot
```

## Control del plugin

La tool `browser` default es un plugin bundled. Los defaults necesitan `plugins.entries.browser.enabled` **y** `browser.enabled=true`. Deshabilitar solo el plugin quita el CLI `openclaw browser`, el method `browser.request` del gateway, la tool de agente y el servicio de control como una sola unidad.

Si `openclaw browser` es desconocido tras un upgrade, la causa usual es un `plugins.allow` que omite `browser` y no existe un bloque raíz `browser`. Añadan `browser` a `plugins.allow`, o cualquier bloque raíz `browser`. `plugins.entries.browser.enabled=true` y `tools.alsoAllow: ["browser"]` **no** sustituyen la membresía del allowlist por si solos (OpenClaw, *Browser*, s. f.).

Nota de perfil de tools: `tools.profile: "coding"` incluye `web_search` y `web_fetch`, pero **no** la tool `browser` completa. Añadan browser en la etapa de perfil con `tools.alsoAllow: ["browser"]`. Para un agente, `agents.entries.*.tools.alsoAllow: ["browser"]`. `tools.subagents.tools.allow: ["browser"]` solo no basta porque la política de sub-agente se aplica después del filtrado de perfil.

<Callout>
La navegación del browser es SSRF fail-closed incluso si omites `browser.ssrfPolicy`. No la relajen por defecto. Prefieran `allowedHostnames` estrechos sobre `dangerouslyAllowPrivateNetwork`. El `HTTP_PROXY` del Gateway no proxifica automáticamente el browser gestionado, así que el proxy del proveedor no puede debilitar las cheques SSRF del browser (OpenClaw, *Browser*, s. f.).
</Callout>

## Plano de control y puertos

El servicio de control se bindea a loopback en un puerto derivado de `gateway.port` (default `18791` = gateway más 2). `OPENCLAW_GATEWAY_PORT` tiene prioridad. Los perfiles locales `openclaw` auto-asignan `cdpPort` desde un rango que empieza 9 puertos por encima del control (default `18800`-`18899`). Los puertos dedicados evitan colisiones con `9222` de workflows de desarrollo (OpenClaw, *Browser*, s. f.).

Los cambios de config de browser exigen un restart del Gateway para que el plugin re-registre su servicio.

La API HTTP standalone de browser en loopback usa **solo auth de secreto compartido**: bearer de token del gateway, `x-openclaw-password`, o HTTP Basic con el password del gateway. Los headers de identidad de Tailscale Serve y `gateway.auth.mode: "trusted-proxy"` **no** autentican esta API standalone de browser en loopback.

## Garantías de aislamiento

- User data dir dedicado: nunca toca tu perfil personal.
- Puertos dedicados: evita `9222`.
- Control determinista de tabs: `tabs` devuelve `suggestedTargetId` primero, luego handles estables `tabId` como `t1`.
- El cleanup de tabs de sesión aplica solo a tabs creados por la tool browser con `action: "open"`. OpenClaw no adopta tabs que ya estaban abiertos.

En macOS puedes copiar cookies de un perfil de sistema Chrome-family a un perfil gestionado separado. Solo se copian las cookies seleccionadas; local storage e IndexedDB se quedan atrás.

## Proxy de browser de nodo

Si corres un **node host** en la máquina que tiene el browser, OpenClaw puede auto-enrutar llamadas de la tool browser a ese nodo sin config extra de browser. Este es el camino default para gateways remotos. Los perfiles vienen del `browser.profiles` del propio nodo. El proxy nunca permite mutaciones persistentes de perfil (`create-profile`, `delete-profile`, `reset-profile`). Deshabiliten con `nodeHost.browserProxy.enabled=false` en el nodo, o `gateway.nodes.browser.mode="off"` en el gateway (OpenClaw, *Browser*, s. f.).

La tool de agente acepta `target` `sandbox`, `host` o `node`. En sesiones sandboxed, `target: "host"` exige `agents.defaults.sandbox.browser.allowHostControl=true`. Si se omite `target`: las sesiones sandboxed defaultan a `sandbox`, las no-sandbox a `host`. Si hay un nodo capaz de browser conectado, la tool puede auto-enrutar salvo que fijen `target`.

**Caso.** Un agente coding no puede hacer click. El perfil es `coding`, que tiene `web_fetch` pero no `browser`. `alsoAllow` browser en la capa de perfil o agente, confirmen que `plugins.allow` incluye `browser`, reinicien el Gateway (OpenClaw, *Browser*, s. f.).

## Comparar, sin mezclar knobs

<VisualSlot id="openclaw-browser:3" />

La automatización de browser de Hermes, cuando existe, es una tool de Hermes dentro de `AIAgent` (Nous Research, *Agent Loop Internals*, s. f., https://hermes-agent.nousresearch.com/docs/developer-guide/agent-loop). El browser de OpenClaw es un servicio de control loopback poseído por el Gateway más un plugin bundled. No peguen un snippet de launch de Playwright en `browser.profiles` y lo llamen oficial. Citen *Browser* para perfiles, SSRF y proxy de nodo.

Fallo de startup CDP y bloqueo SSRF de navegación son clases distintas. Si `start` falla, depuren readiness CDP. Si `start` y `tabs` cubren pero `open` falla, el plano de control esta arriba y el fallo es política de navegación (OpenClaw, *Browser*, s. f.).

`attachOnly: true` significa nunca lanzar un browser local; solo adjuntar si uno ya corre. Browserless en loopback sin `attachOnly` se trata como perfil local gestionado por OpenClaw y puede reportar que el puerto está en uso pero no es de OpenClaw.

Existing-session vía Chrome MCP es más riesgoso que el `openclaw` aislado porque puede actuar dentro de tu sesión iniciada. Chrome debe ser versión 144+. Tras restart del subprocess MCP, corran `browser tabs` otra vez y tomen un snapshot nuevo antes de usar refs. Las refs solo valen para su target y el snapshot más reciente.

El skill bundled `browser-automation` enseña snapshot, tab estable, stale-ref y recuperación de blockers manuales cuando el plugin está habilitado. Los skills bundled del plugin se listan cuando el plugin esta on; las instrucciones completas cargan on demand.

Los perfiles Playwright-backed guardan navegaciones de attachment bajo el directorio gestionado de downloads y devuelven url, suggestedFilename y path tras validación de política de URL final. No inventen campos extra de download.

Las URLs CDP remotas pueden incluir tokens de query o HTTP Basic. Tratenlas como secretos; prefieran env vars. Usen el driver regular `openclaw` para Browserless, Browserbase o Notte. Los perfiles `existing-session` con `cdpUrl` explícito se rechazan bajo la política estricta default porque Chrome MCP no puede llevar el lookup DNS pineado de OpenClaw a través de su frontera de subprocess.

Hosts Linux sin `DISPLAY` ni `WAYLAND_DISPLAY` defaultan perfiles locales gestionados a headless. `openclaw browser --json status` reporta `headlessSource` como `env`, `profile`, `config`, `request`, `linux-display-fallback` o `default`.

Vision de screenshot: cuando el modelo main es solo-texto, los screenshots reutilizan `tools.media.models` y envuelven la descripción con `wrapExternalContent`. Los bloques de imagen de screenshot son resultados privados de tool; OpenClaw no los adjunta automáticamente a replies de canal (OpenClaw, *Browser*, s. f.).

`evaluateEnabled` defaulta true; pongan false para deshabilitar `act:evaluate` (JS arbitrario). Eso es un cuchillo separado de SSRF.

Esta lección se detiene en perfiles, allowlist de plugin, control loopback, defaults SSRF y proxy de nodo. El host-control de sandbox continua en la lección de sandbox. ACP no envuelve este browser; un harness spawned usa sus propias tools salvo que habiliten puentes MCP de ACPX.

Lectura adicional: *Browser control API*, *Chrome extension*, *Sandboxing*, *Security*, *WSL2 + Windows + remote Chrome CDP troubleshooting* (OpenClaw, s. f.).

El comportamiento de stop difiere por modo: `stop` de managed local mata el proceso que OpenClaw lanzo; `stop` de attach-only y CDP remoto solo cierra la sesión de control y libera overrides de emulación Playwright/CDP.

La ownership de cleanup de tabs se guarda en SQLite compartida para opens host-local con un target CDP nativo estable. Esos records sobreviven restart del Gateway. Los handles de Chrome MCP son process-local, así que los records existing-session frios esperan cleanup de ciclo de vida en vez de arriesgar un idle sweep tras restart.

No usen Funnel para control de browser; traten el pairing de nodo como acceso de operador. Citen *Tailscale* para esa frase (OpenClaw, *Tailscale*, s. f., https://docs.openclaw.ai/gateway/tailscale).

**Caso.** Gateway remoto en un VPS, Chrome en un laptop. Corran un node host en el laptop, mantengan ambos en el mismo tailnet, dejen el proxy de browser en auto. No hagan Funnel del puerto de control de browser (OpenClaw, *Browser*, s. f.; *Tailscale*, s. f.).

`noSandbox` en la config de browser es el flag de sandbox de Chromium para el Chrome gestionado, no `agents.defaults.sandbox` de OpenClaw. Mezclar esas dos palabras "sandbox" es como alguien desactiva el aislamiento de Chromium pensando que toggleo la jaula del agente.

La particularidad: el agente no conduce tu Chrome diario salvo que elijan `user` o `chrome`. El default es un perfil separado en loopback, detrás de auth del Gateway, detrás de SSRF fail-closed.

Doctor migra config vieja basada en extension y chequea que Chrome este instalado para perfiles auto-connect default, pero no puede habilitar remote debugging del lado del browser por ustedes. Alguien sigue teniendo que hacer click Allow en el attach `user`.

Arquitectura relacionada: el Gateway posee el servicio de control; los nodos opcionalmente lo proxifican. Un Gateway por host se mantiene. Dos Gateways lanzando Chrome en 18800 es una pelea de puertos, no un cluster (OpenClaw, *Gateway architecture*, s. f., https://docs.openclaw.ai/concepts/architecture).

Cuando una sesión sandboxed necesita el browser del host, eso es un opt-in explícito `allowHostControl`, no un efecto secundario de `tools.alsoAllow`. Citen *Sandboxing* (OpenClaw, s. f., https://docs.openclaw.ai/gateway/sandboxing).

Las interacciones Playwright guardadas interceptan loads de documento denegados por política antes de bytes HTTP durante la acción y una gracia acotada post-acción. El routing de Playwright sigue sin ser un firewall de red: no intercepta hops de redirect, el primer request de un popup, tráfico de Service Worker ni cada path de fondo. El aislamiento completo de egress exige aislamiento del owner o un proxy que aplique política (OpenClaw, *Browser*, s. f.).

En modo SSRF estricto, el discovery de endpoints CDP remotos y las probes `/json/version` también se chequean. Redirigir el discovery CDP a otra autoridad permanece sin soporte salvo que la política activa permita ese cambio de autoridad.

Para proxificar el browser gestionado, pasen flags explícitos de Chrome vía `browser.extraArgs`, como `--proxy-server`. El modo SSRF estricto bloquea routing explícito de proxy de browser salvo que el acceso a red privada este intencionalmente habilitado.

El orden de auto-detect al lanzar local: default del sistema si es Chromium-based; si no Chrome, Brave, Edge, Chromium, Chrome Canary. Override con `browser.executablePath`.

`browser snapshot` devuelve un árbol UI estable (AI o ARIA). `browser navigate` también devuelve el snapshot de la página cargada inline. `browser act` usa ids `ref` del snapshot. Los snapshots efficient omiten la mayor parte de prosa no interactiva a propósito.

Si la comprensión de imagen no está disponible, se salta o falla, el browser cae a devolver el bloque de imagen original. El wrap usa guards de prompt-injection; traten las descripciones de screenshot como contenido de página no confiable.

No inventen un `browser.incognito` que mapee a incognito de sesión. Los perfiles de browser y el incognito de sesión son stores distintos.

**Caso.** `start` y `tabs` funcionan, `open https://127.0.0.1:3000 falla. Eso es SSRF de navegación, no un CDP muerto. Dejen la política estricta; añadan una excepción exacta de hostname solo si el acceso de browser a red privada está revisado (OpenClaw, *Browser*, s. f.).

Citen *Browser control API* para la superficie HTTP loopback. Esta lección no vuelca cada query parameter.

El Control UI no es un segundo driver de browser. Los agentes conducen tabs vía la tool `browser`.

Cuando `evaluateEnabled` es false, el JS arbitrario vía `act:evaluate` desaparece; snapshots y clicks quedan. Así se reduce la superficie de ataque JS sin deshabilitar el plugin entero.

Mantengan el Gateway y los node hosts en una red privada. Eviten exposición publica de URLs CDP. Funnel es el remoto equivocado para esta superficie.

Status y doctor para un perfil local gestionado en marcha consultan el endpoint CDP a nivel browser. Una llamada pasiva de status no lanza Chrome. Existing-session, extension, CDP remoto y browsers de sandbox no se inspeccionan por este camino managed-host.

Headless managed Chrome sigue usando el default conservador `--disable-gpu`. Los diagnósticos no habilitan aceleración ni otorgan acceso de dispositivo al browser de sandbox.

`userDataDir` en un perfil existing-session apunta a Brave, Edge o un perfil Chrome no default. La tilde se expande al home del OS. Cuando `cdpUrl` está puesto en existing-session, `userDataDir` se ignora.

## Caso — el perfil de Chrome que se mezcló

Un agente usaba el perfil user de Chrome y tocó las pestañas del humano. El perfil dedicado de OpenClaw existe para eso: el agente corre en su propio perfil, aislado del tuyo. Mezclar perfiles es cómo un agente borra una pestaña que no era suya.
