## Una herramienta es una función tipada que tú ejecutas

se le da al modelo. El modelo no puede llamarla. Solo puede emitir texto que *parece* una llamada. El arnés lee ese texto, ejecuta el callable y devuelve el resultado.

*Fuente nombrada: Hugging Face Agents Course, Unidad 1, [What are Tools?](https://huggingface.co/learn/agents-course/unit1/tools) y [Actions](https://huggingface.co/learn/agents-course/unit1/actions) (Burtenshaw, Thomas, Simonini y Paniego, Apache-2.0).*

Una buena tool complementa al modelo. La aritmética vive en una calculadora, no en los logits. El tiempo de hoy vive en una API, no en la fecha de corte del entrenamiento. Generar imágenes, recuperar documentos, un cliente de GitHub: la misma forma.

El LLM solo recibe texto y solo emite texto. «Dar tools a un agente» es enseñarle que existen e instruirle a generar invocaciones en texto. El arnés hace el resto, fuera de cámara. El usuario ve una respuesta natural. Tú ves un despacho.

<VisualSlot caption="Esquema → registro → pulso de despacho → puerta de política → backend." />

Tu runtime, en un turno:

1. Expone **esquemas** visibles este turno.
2. Busca el nombre en un **registro** (registry).
3. Aplica **política** (allow/deny, aprobaciones, sandbox).

Cinco cajas. Si saltas la puerta de política, el modelo «tiene bash» de verdad. Si saltas el registro, ejecutas un nombre alucinado. Si saltas el esquema, el modelo no sabe qué pedir.

Otros ejemplos que el curso pone en la misma tabla: búsqueda web, generar imagen, retrieval, un cliente de API (GitHub, YouTube, Spotify). La forma no cambia. Cambia el backend. Un retrieval es un handler que consulta un índice; no es un segundo decoder. Si el esquema dice search y el handler abre bash, la puerta de política ha fallado en silencio.


## Qué tiene que llevar una tool

El curso pide cuatro piezas, siempre:

- un **nombre**
- una **descripción textual** del objetivo
- **argumentos** con tipos
- opcionalmente **salidas** con tipos

Más el **callable**: algo que de verdad corre. Sin callable tienes un diccionario de marketing. Sin descripción tienes un modelo que inventa argumentos.

El ejemplo de calculadora de la Unidad 1 es una función de una línea que multiplica dos enteros:

    def calculator(a: int, b: int) -> int:
        # Multiply two integers.
        return a * b

La forma textual que el modelo necesita ver — exactamente la cadena del curso — es:

    Tool Name: calculator, Description: Multiply two integers., Arguments: a: int, b: int, Outputs: int

Eso va al system prompt. No un objeto Python. No un plugin invisible. Texto. Si añades otra tool, el mismo formato, siempre. El proceso es frágil: un detalle omitido y el modelo improvisa.

smolagents (y el decorador que el curso bosqueja) extraen nombre, docstring y type hints para no escribir esa cadena a mano. Hasta entonces, el prompt dummy **ya contiene** la lista. Nada se descubre en runtime. Si la descripción es vaga, el modelo inventará argumentos. Si dos tools se solapan, elegirá la equivocada. La precisión del system prompt es el producto.

Cómo se le **dan** las tools al modelo, en una frase: el system prompt lleva descripciones textuales, precisas. JSON o un mini-lenguaje sirven porque son coherentes, no porque el decoder «entienda JSON». Cualquier formato preciso vale; mezclar dos en el mismo prompt no.

El curso bosqueja una clase Tool con name, description, func, arguments, outputs, un to_string que pinta la cadena de arriba, y un call que invoca el callable. No copies esa clase aquí con literales. La idea: el prompt ve to_string; el runtime ve call. Si solo tienes una de las dos, no tienes una tool.

<Callout>
El LLM solo maneja texto. Describe la acción que quiere y los parámetros. Para que el agente funcione, la generación debe **parar** después de una Action completa para que un parser la lea. Tokens de más después de la Action no son creatividad. Son un contrato roto.
</Callout>

## Stop-and-parse

Actions de la Unidad 1: el decoder emite una Action en un formato pactado y **para**. Un parser externo lee el nombre y los argumentos. Sin parada, el modelo sigue y el parser recibe basura. Sin parser, la parada es un cuelgue.

Tres grafías del mismo hueco:

- **Agente JSON** — el dummy. Un objeto con action y action_input. Un parser mapea el nombre a la función.
- **Agente de código** — un bloque Python que un intérprete ejecuta. Bucles, varias llamadas, variables. Más expresivo. Más peligroso. El default de [smolagents](/es/m/smolagents).
- **Agente de function-calling** — un JSON cuya plantilla de chat creció roles especiales: un mensaje assistant que es una llamada, un mensaje tool que es la Observation. Aprendido, no solo inducido. Ver [function-calling](/es/m/function-calling-ft).

Los tres siguen haciendo stop-and-parse. Los de código delimitan un bloque y tratan un print de respuesta final como fin de paso. Los de function-calling paran porque la API devuelve tool_calls en vez de contenido. El dummy deja la cadena de stop a la vista.

<Compare a="JSON / function-calling" b="Agente de código">
<Side>
Una llamada por Action. El parser es un mapa nombre → función. El sandbox puede ser más estrecho. El dummy cabe en veinte líneas.
</Side>
<Side>
Un bloque con lógica. Más potencia, más superficie. Ejecutar código generado por un LLM es un riesgo (inyección, daños). El curso recomienda un framework con salvaguardas — smolagents las trae por defecto. No las apagues para «ir más rápido».
</Side>
</Compare>

Un code agent que llama al tiempo no emite action=get_weather. Escribe Python, importa un cliente, imprime. Tú interpretas en un sandbox, no en el kernel del host. Si no hay sandbox, no tienes un agente de código. Tienes un shell con un system prompt educado.

El while de veinte líneas, el stop y el parser estricto: [agente dummy](/es/m/dummy-agent). Esta lección es el despacho alrededor de ese hueco.

## De la cadena al backend

El curso se queda en «el Agent ejecuta». iAguide nombra las cajas, porque ahí se pudre el producto:

**Esquema.** Lo que el modelo ve este turno. Si la política quita una tool, el esquema no se pinta. El modelo no puede pedir lo que no ha leído.

**Registro.** Nombre → handler. Hermes descubre el registro a nivel de módulo; sombrear un nombre exige override y consentimiento. Un nombre que no está no se ejecuta. El modelo lo intentará.

**Despacho.** El pulso: parsear, validar tipos, llamar. Aquí vive el stop-and-parse.

**Política.** Allow/deny, aprobaciones humanas, sandbox. OpenClaw filtra por perfil, allow/deny, sandbox y plugins. Si la política quita una tool, el modelo no ve su esquema. Esa es la puerta. No un «por favor» en el system prompt.

**Backend.** Dónde corre de verdad: proceso local, contenedor, SSH, un node con Chrome. Terminal y browser no son segundos cerebros. Hermes tiene varios backends de terminal; OpenClaw puede mandar browser a sandbox, host o un node con Chrome vía el Gateway.

<Myth>
«El modelo tiene bash.» No. Emite un tool_call. Si tu política y tu backend le dan un shell, *tú* le diste bash. El decoder sigue prediciendo tokens.
</Myth>

Consejo práctico: nombra las cinco cajas en el código como las nombra el diagrama. Si el log dice solo «LLM», no sabrás si falló el esquema, la puerta o el backend.
