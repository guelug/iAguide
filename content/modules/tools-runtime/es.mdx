## Una herramienta es una función tipada que tú ejecutas

El modelo no «tiene bash». Emite un <Term id="tool-call">tool_call</Term>. Tu arnés:

1. Expone **esquemas** visibles este turno.
2. Busca el nombre en un **registro** (registry).
3. Aplica **política** (allow/deny, aprobaciones, sandbox).
4. Ejecuta un **handler** (o un **backend**: terminal local, Docker, SSH, CDP…).
5. Añade el resultado como mensaje y sigue el bucle.

<VisualSlot caption="Esquema → registro → pulso de despacho → puerta de política → backend. Los permisos están entre el modelo y el host." />

*Fuente nombrada: Hugging Face Agents Course, Unidad 1, [What are Tools?](https://huggingface.co/learn/agents-course/unit1/tools) (Burtenshaw, Thomas, Simonini y Paniego, Apache-2.0).*

Una buena tool complementa al modelo. La aritmética vive en una calculadora, no en los logits. El tiempo de hoy vive en una API, no en la fecha de corte del entrenamiento. Generar imágenes, recuperar documentos, un cliente de GitHub: la misma forma.

El LLM solo maneja texto. Describe la acción que quiere y los parámetros. Tú haces el resto. El usuario ve una respuesta natural. Tú ves un despacho.

## Las cinco cajas del runtime

### Esquema

Lo que el modelo ve este turno. Una tool sin esquema visible es una tool que no existe para el modelo. El esquema es un JSON Schema (o equivalente): nombre, descripción, parámetros con tipos. Si pones herramientas con nombres ambiguos, el modelo pedirá la equivocada. Si la descripción es vaga, inventará argumentos.

El curso de Hugging Face recomienda cuatro piezas siempre:
- Un **nombre** único
- Una **descripción textual** del objetivo
- **Argumentos** con tipos
- Opcionalmente **salidas** con tipos

Y un **callable**: algo que de verdad corre. Sin callable tienes un diccionario de marketing. Sin descripción tienes un modelo que adivina.

### Registro

Nombre → handler. Hermes descubre el registro a nivel de módulo; sombrear un nombre exige `override=True` más consentimiento. OpenClaw filtra tools por perfil, allow/deny, restricciones de proveedor y políticas de sandbox. Si el registro no tiene el nombre, no se ejecuta, aunque el modelo lo pida.

### Despacho

El pulso: parsear, validar tipos, llamar al handler. Aquí vive el stop-and-parse del ciclo ReAct. El curso llama a esto «el Agent ejecuta». Internamente es: leer el tool_call, sacar el nombre y los argumentos, comprobar que el nombre está en el registro, llamar.

### Política

Allow/deny, aprobaciones humanas, sandbox. Si la política quita una tool, el modelo no ve su esquema. Esa es la puerta. No un «por favor» en el system prompt.

<Myth>
«El modelo tiene bash.» No. Emite un tool_call. Si tu política y tu backend le dan un shell, *tú* le diste bash. El decoder sigue prediciendo tokens. La seguridad no está en el modelo; está en las cinco cajas.
</Myth>

### Backend

Dónde corre de verdad. Hermes terminal backends incluyen local, Docker, SSH, Daytona, Modal, Singularity, Vercel Sandbox. OpenClaw browser puede targetizar sandbox, host o un node emparejado con Chrome; Gateway hace de proxy, no hace falta exponer el puerto del browser.

Terminal y browser no son segundos cerebros. Son backends detrás de tools.

<Compare a="Plugin" b="Builtin">
<Side>
Se registra sin tocar el núcleo: hooks, herramientas nuevas, plataformas. Preferible para tools personales o de proveedor.
</Side>
<Side>
Viene en el árbol principal. Útil para el núcleo del arnés. Cada builtin adicional es una rama que pagas en cada llamada.
</Side>
</Compare>

## Plugins vs builtins vs skills

- **Builtin** — vive en el árbol del núcleo. Hermes los auto-descubre con `registry.register()`.
- **Plugin** — se registra por API de contexto sin forkear el núcleo. Preferible para tools personales.
- **Skill** — instrucciones + tools existentes (`SKILL.md`), no un callable nuevo, cuando un flujo de trabajo basta.

Un skill no es una tool. Es una receta que usa tools. Si lo que necesitas es «busca en la web y resume», un skill con instrucciones y `web_search` puede bastar. Si necesitas un callable nuevo, es un plugin o un builtin.

## El stop-and-parse en detalle

El curso hace hincapié en que el modelo **pare** después de emitir la Action. Si no paras, el modelo escribe la Observation y tienes una alucinación con datos falsos. El truco es una secuencia de stop.

Tres grafías del mismo hueco:

- **Agente JSON** — el modelo emite un objeto JSON con `action` y `action_input`. El parser lo mapea a la función.
- **Agente de código** — un bloque Python que se ejecuta en sandbox. Más expresivo. El default de [smolagents](/es/m/smolagents).
- **Agente de function-calling** — el modelo emite un `tool_calls` nativo del API de chat. El proveedor lo parsea por ti.

Los tres hacen stop-and-parse. Los de código delimitan un bloque. Los de function-calling paran porque el API devuelve `tool_calls` en vez de `content`. El dummy deja la cadena de stop a la vista.

## El while de veinte líneas

El curso implementa el ciclo en la [Dummy Agent Library](https://huggingface.co/learn/agents-course/unit1/dummy-agent-library). La forma del bucle, sin copiar literales que rompan el MDX:

1. El arnés construye los mensajes: system prompt + historial + nueva pregunta.
2. Llama al modelo con `stop=["Observation:"]`.
3. El modelo devuelve Thought + Action JSON.
4. Parseas el Action: ¿es un nombre conocido? ¿tiene los argumentos correctos?
5. Ejecutas la función (o devuelves error).
6. Añades la Observation real al mensaje.
7. Repites hasta `Final Answer:` o tope de pasos.

Ese while cabe en veinte líneas. Esa es la herramienta más importante del curso.

<Callout>
`stop=["Observation:"]` no es adorno. Sin él, el modelo escribe la Observation y tienes un chatbot que hace teatro de tools. Con él y sin `runTool`, tienes un cuelgue. Ambos bugs parecen agentes en una demo. Ninguno lo es.
</Callout>

## Prefill, decode y A3B en el runtime de tools

Cuando el modelo decide llamar a una tool, el flujo es:

1. **Generate** (decode): el modelo emite el tool_call token a token. Es decode: memory-bandwidth-bound, un token cada vez.
2. **Ejecución**: tu código corre la tool. Esto puede ser rápido (una calculadora) o lento (una API HTTP, un browser). El modelo no espera; el arnés espera.
3. **Append**: añades el resultado como mensaje de tool.
4. **Nuevo prefill**: el arnés llama al modelo otra vez. Prefill procesa el contexto actualizado (TOOOOODOS los tokens) en paralelo.

Aquí hay un detalle importante con modelos **A3B/MoE** (como Kimi Linear 48B-A3B): durante el prefill, aunque solo ~3B parámetros estén activos por token, la atención sigue siendo *dense* sobre toda la caché KV. Eso significa que el **prefill escala con la longitud del contexto**, no con los parámetros activos. Un modelo A3B con 100k tokens de contexto va a tener un prefill pesado igual que uno dense de 3B. La ventaja del A3B está en el **decode** (menos FLOPs por token porque solo activas 3B de los 48B), pero la **memoria** sigue teniendo que cargar los 48B completos.

Por eso una tool que devuelve mucho texto (una página web entera, un PDF parseado) encarece el siguiente prefill. La compactación no es opcional; es económica.

<Myth>
«Un modelo A3B necesita menos VRAM porque solo usa 3B parámetros.» Falso. Necesita VRAM para los **48B parámetros totales**. Los 3B activos afectan a los FLOPs por token, no al tamaño en memoria.
</Myth>

## Anatomía de un tool_call (en crudo)

Un tool_call es un mensaje estructurado. El API devuelve algo como:

| Campo | Valor |
|---|---|
| `id` | `call_abc123` |
| `type` | `function` |
| `function.name` | `get_weather` |
| `function.arguments` | `{"location": "Madrid"}` |

El arnés busca `get_weather` en el registro, valida que `location` es string, ejecuta el handler y devuelve un tool_result con el mismo `id` para que el modelo pueda correlacionarlo.

Si el JSON de arguments viene mal formado (comillas rotas, tipos equivocados), el handler no debe ejecutarse. Rechazar y devolver un error de parseo es más seguro que ejecutar con argumentos basura.

## Caso — el plugin que editaba el núcleo

**Caso.** Un contribuidor parchea `run_agent.py` para añadir su SaaS en lugar de usar `ctx.register_tool(...)`.

**Olor.** El núcleo es una cintura estrecha; cada rama especial afecta a todas las llamadas API. Ensancha la superficie de plugins; mantén el bucle aburrido. Una tool nueva no debería tocar el loop; debería registrarse como plugin.

## Caso — GooSearch y el solapamiento de nombres

**Caso.** Dos plugins registran `web_search` con distinta implementación. Sin un sistema de override, el último en cargar gana y el primero deja de funcionar sin aviso.

**Lección.** Nombres únicos, override explícito con consentimiento, log del ganador. Hermes rechaza sombrear sin `override=True`. OpenClaw filtra por perfil. No asumas que «el último que se registra es el mejor».
