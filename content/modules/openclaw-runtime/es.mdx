## El loop embebido es el default

La fuente primaria es [*Agent runtimes*](https://docs.openclaw.ai/concepts/agent-runtimes) de OpenClaw (s. f.). Un **agent runtime** posee un loop de modelo preparado: recibe el prompt, conduce la salida del modelo, maneja tool calls nativas y devuelve el turno terminado a OpenClaw. [*Agent runtime*](https://docs.openclaw.ai/concepts/agent) (OpenClaw, s. f.) enuncia el contrato del loop embebido que esta lección implementa.

La lección genérica [agent loop](/es/m/agent-loop) permanece agnóstica del harness. Esta es cual loop posee el turno.

Los runtimes se confunden fácil con providers porque ambos aparecen cerca de la config de modelo. Son capas distintas (OpenClaw, *Agent runtimes*, s. f.):

| Capa | Ejemplos | Significado |
| --- | --- | --- |
| Provider | `anthropic`, `github-copilot`, `openai` | Como OpenClaw autentica, descubre modelos y nombra refs |
| Model | `claude-opus-4-6`, `gpt-5.6-sol` | El modelo seleccionado para el turno de agente |
| Agent runtime | `claude-cli`, `codex`, `copilot`, `openclaw` | El loop o backend de bajo nivel que ejecuta el turno preparado |
| Channel | Discord, Slack, Telegram, WhatsApp | Donde los mensajes entran y salen de OpenClaw |

Un **harness** es la implementación que provee un agent runtime (termino de código). Por ejemplo, el harness Codex bundled implementa el runtime `codex`. La config publica usa `agentRuntime.id` en entradas de provider o modelo; las claves de runtime de agente entero son legacy y se ignoran. `openclaw doctor --fix` quita pins viejos de runtime de agente entero y reescribe refs de modelo legacy a refs canónicos provider/model más política de runtime con alcance de modelo donde hace falta.

## Dos familias de runtime

- **Harnesses embebidos** corren dentro del loop de agente preparado de OpenClaw: el runtime built-in `openclaw`, más harnesses de plugin registrados como `codex` y `copilot`.
- **CLI backends** corren un proceso CLI local manteniendo la ref de modelo canónica. Por ejemplo, `anthropic/claude-opus-5` con un `agentRuntime.id: "claude-cli"` de alcance de modelo significa "selecciona el modelo Anthropic, ejecuta por Claude CLI." `claude-cli` no es un id de harness embebido y no debe pasarse a la selección AgentHarness (OpenClaw, *Agent runtimes*, s. f.).

El harness `copilot` es un plugin externo opt-in para GitHub Copilot CLI. Reclama el provider de suscripción canónico `github-copilot` y **nunca** lo selecciona `auto`. Opta por modelo o por provider vía `agentRuntime.id` (OpenClaw, *Agent runtimes*, s. f.; *GitHub Copilot agent runtime*, s. f., https://docs.openclaw.ai/plugins/copilot).

## Superficies Codex comparten nombre

Varias superficies comparten el nombre Codex. Copia la tabla en la respuesta de TryThis. No las colapses en un solo knob.

| Superficie | Nombre/config OpenClaw | Que hace |
| --- | --- | --- |
| Runtime nativo Codex app-server | refs de modelo `openai/*` | Corre turnos de agente embebidos OpenAI por Codex app-server. Setup usual de suscripción ChatGPT/Codex |
| Perfiles OAuth Codex | perfiles OAuth `openai` | Guarda auth de suscripción ChatGPT/Codex que consume el harness Codex app-server |
| Adapter ACP Codex | `runtime: "acp"`, `agentId: "codex"` | Corre Codex por el plano de control externo ACP/acpx. Úsalo solo cuando se pide ACP/acpx de forma explícita |
| Conjunto de commands de chat-control nativo Codex | `/codex ...` | Bind, resume, steer, stop e inspección de threads Codex app-server desde el chat |
| Ruta API OpenAI Platform para superficies no-agente | `openai/*` más auth de API-key | APIs OpenAI directas: images, embeddings, speech, realtime |

Estas superficies son independientes a propósito. Habilitar el plugin `codex` hace disponibles las features nativas de app-server. Seleccionar `openai/*` para un modelo de agente ahora significa "corre esto por Codex" salvo que se use una superficie API OpenAI no-agente (OpenClaw, *Agent runtimes*, s. f.).

Cuando el plugin bundled `codex` está habilitado, usa la superficie nativa `/codex` (`/codex bind`, `/codex threads`, `/codex resume`, `/codex steer`, `/codex stop`) para control Codex en lenguaje natural en vez de ACP. Usa ACP para Codex solo cuando el usuario pide ACP/acpx de forma explícita o está probando el camino adapter ACP. Claude Code, Gemini CLI, OpenCode, Cursor y harnesses externos similares siguen usando ACP.

<Callout>
ACP es el camino de harness externo, no el camino Codex por defecto. El plugin nativo Codex app-server posee los controles `/codex ...` y el runtime embebido default `openai/gpt-*` para turnos de agente; ACP posee los controles `/acp ...` y `sessions_spawn` con `runtime: "acp"` (OpenClaw, *ACP agents*, s. f., https://docs.openclaw.ai/tools/acp-agents).
</Callout>

## Ownership de runtime

Distintos runtimes poseen distintas cantidades del loop (OpenClaw, *Agent runtimes*, s. f.):

| Superficie | OpenClaw embebido | Codex app-server |
| --- | --- | --- |
| Owner del loop de modelo | OpenClaw, vía el runner embebido OpenClaw | Codex app-server |
| Estado canónico de thread | transcript OpenClaw | thread Codex, más espejo de transcript OpenClaw |
| Tools dinámicas OpenClaw | loop nativo de tools OpenClaw | puenteadas por el adapter Codex |
| Tools nativas de shell y archivos | camino OpenClaw | tools nativas Codex, puenteadas por hooks nativos donde se soporta |
| Context engine | ensamblado nativo OpenClaw | OpenClaw proyecta contexto ensamblado al turno Codex |
| Compaction | OpenClaw o context engine seleccionado | compaction nativa Codex, con notificaciones OpenClaw y mantenimiento de espejo |
| Entrega de canal | OpenClaw | OpenClaw |

Regla de diseño: si OpenClaw posee la superficie, puede dar conducta normal de hooks de plugin. Si el runtime nativo posee la superficie, OpenClaw necesita eventos de runtime o hooks nativos. Si el runtime nativo posee el estado canónico de thread, OpenClaw espeja y proyecta contexto en vez de reescribir internos no soportados.

## Selección de runtime

OpenClaw resuelve un runtime embebido después de resolver provider y modelo, en este orden (OpenClaw, *Agent runtimes*, s. f.):

1. **Política de runtime de alcance de modelo** gana. Vive en una entrada de modelo de provider, o en `agents.defaults.models["provider/model"].agentRuntime` / `agents.entries.*.models["provider/model"].agentRuntime`. Un wildcard de provider como `agents.defaults.models["vllm/*"].agentRuntime` aplica después de la política exacta de modelo.
2. **Política de runtime de alcance de provider**: `models.providers.<id>.agentRuntime`.
3. **Modo `auto`**: los runtimes de plugin registrados pueden reclamar pares provider/model soportados.
4. Si nada reclama el turno en modo `auto`, OpenClaw cae a `openclaw` como runtime de compatibilidad. Usa un id de runtime explícito cuando la corrida debe ser estricta.

Los pins de runtime de sesión entera y de agente entero se ignoran: `OPENCLAW_AGENT_RUNTIME`, estado de sesión `agentHarnessId` / `agentRuntimeOverride`, `agents.defaults.agentRuntime` y `agents.entries.*.agentRuntime`. Ejecuta `openclaw doctor --fix` para quitar config stale de runtime de agente entero.

Los runtimes de plugin explícitos de provider/model fallan cerrados: `agentRuntime.id: "codex"` en un provider o modelo significa Codex, o un error claro de selección/runtime. Nunca se enruta en silencio de vuelta a OpenClaw. Solo `auto` puede enrutar un turno no reclamado a OpenClaw.

El modo `auto` es conservador a propósito para la mayoría de providers. Los modelos de agente OpenAI son la excepción: runtime no fijado y `auto` resuelven ambos al harness Codex. La config explícita de runtime OpenClaw permanece un camino de compatibilidad opt-in para turnos de agente `openai/*`.

La forma preferida de Claude CLI mantiene el provider/model canónico y pone el backend de ejecución en la política de runtime de provider/model:

```json5
{
  agents: {
    defaults: {
      model: "anthropic/claude-opus-5",
      models: {
        "anthropic/claude-opus-5": {
          agentRuntime: { id: "claude-cli" },
        },
      },
    },
  },
}
```

Refs legacy como `claude-cli/claude-opus-4-7` se aceptan como entrada de compatibilidad. Las refs legacy `codex-cli/*` son distintas: doctor las migra a `openai/*` para que corran por el harness Codex app-server en vez de preservar un backend Codex CLI.

## Árbol de decisión

1. **Codex bind/control/thread/resume/steer/stop** entonces `/codex` nativo cuando el plugin bundled `codex` está habilitado.
2. **Codex como runtime embebido** o la experiencia de agente Codex con suscripción entonces `openai/<model>`.
3. **OpenClaw elegido de forma explícita para un modelo OpenAI** entonces mantén la ref como `openai/<model>` y fija la política de runtime de provider/model a `agentRuntime.id: "openclaw"`.
4. **Refs de modelo Codex legacy en config** entonces repara con `openclaw doctor --fix` a `openai/<model>`.
5. **ACP, acpx o adapter ACP Codex pedido de forma explícita** entonces `runtime: "acp"` y `agentId: "codex"`.
6. **Claude Code, Gemini CLI, OpenCode, Cursor, Droid u otro harness externo** entonces ACP/acpx, no el runtime nativo de sub-agente.

**Caso.** Un operador fija `agents.defaults.model` a `openai/gpt-5.6-sol` y se pregunta por que el loop es Codex. Esa ref ahora significa "corre esto por Codex app-server" salvo que se use una superficie API OpenAI no-agente. Para mantener OpenClaw como loop de ese modelo OpenAI, fija `agentRuntime.id` de alcance de modelo a `openclaw` (OpenClaw, *Agent runtimes*, s. f.).

## Etiquetas de status

La salida de status puede mostrar etiquetas `Execution` y `Runtime`. Léelas como diagnóstico, no como nombres de provider:

- Una ref de modelo como `openai/gpt-5.6-sol` es el provider/model seleccionado.
- Un id de runtime como `codex` es el loop que ejecuta el turno.
- Una etiqueta de canal como Telegram o Discord es donde ocurre la conversación.

Si una corrida muestra un runtime inesperado, inspecciona primero la política de runtime del provider/model seleccionado. Los pins de runtime de sesión legacy ya no deciden el enrutado (OpenClaw, *Agent runtimes*, s. f.).

El runtime de agente embebido es poseído por OpenClaw: descubrimiento de modelo, cableado de tools, ensamblado de prompt, gestión de sesiones y entrega de canal comparten una superficie de runtime integrada (OpenClaw, *Agent runtime*, s. f.).

## Compara, sin mezclar knobs

Hermes tiene un loop: `AIAgent.run_conversation` (Nous Research, *Agent Loop Internals*, s. f., https://hermes-agent.nousresearch.com/docs/developer-guide/agent-loop). OpenClaw tiene un catálogo de runtime: `openclaw` embebido, plugin `codex`, `copilot` opt-in, CLI backend `claude-cli` y spawn ACP para harnesses externos. Misma necesidad humana (un loop de modelo). Distinto límite de proceso.

No pegues `api_mode` de Hermes (`chat_completions`, `codex_responses`, `anthropic_messages`) en `agentRuntime.id` de OpenClaw. No pegues OpenClaw `runtime: "acp"` en un adapter ACP de Hermes; Hermes **es** el servidor ACP que un editor conduce. El spawn ACP de OpenClaw es el inverso: OpenClaw lanza Claude Code o Cursor como harness cliente. El modo bridge `openclaw acp` es el otro inverso: OpenClaw **es** el servidor ACP para editores (OpenClaw, *ACP*, s. f., https://docs.openclaw.ai/cli/acp). Ese split continua en la lección ACP.

**Caso.** Un portátil corre `openclaw acp` para que Zed hable con una sesión Gateway. Eso es modo bridge. `/acp spawn claude --bind here` es la otra dirección: OpenClaw lanza Claude Code. Comparten las letras ACP. No comparten una clave de config (OpenClaw, *ACP*, s. f.; *ACP agents*, s. f.).

La reivindicación de escritor en el camino embebido es la lane de sesión de la lección de cola: una corrida activa por session key. Codex app-server posee su thread; OpenClaw espeja. Los harnesses ACP poseen su filesystem y tools nativas; OpenClaw posee enrutado, estado de background-task, entrega, bindings y política. Cita la página que estas implementando.

## Contrato de compatibilidad

<VisualSlot id="openclaw-runtime:3" />

Cuando un runtime no es OpenClaw, su docs debe enunciar que superficies OpenClaw soporta (OpenClaw, *Agent runtimes*, s. f.):

| Pregunta | Por que importa |
| --- | --- |
| ¿Quién posee el loop de modelo? | Determina donde ocurren retries, continuación de tools y la decisión de respuesta final |
| ¿Quién posee la historia canónica de thread? | Determina si OpenClaw puede editar historia o solo espejarla |
| ¿Funcionan las tools dinámicas OpenClaw? | Messaging, sesiones, cron y tools poseídas por OpenClaw dependen de esto |
| ¿Funcionan los hooks de tools dinámicas? | Los plugins esperan `before_tool_call`, `after_tool_call` y middleware alrededor de tools poseídas por OpenClaw |
| ¿Funcionan los hooks de tools nativas? | Shell, patch y tools poseídas por el runtime necesitan soporte de hook nativo para política y observación |
| ¿Corre el ciclo de vida del context engine? | Memory y plugins de contexto dependen de assemble, ingest, after-turn y compaction |
| ¿Qué datos de compaction se exponen? | Algunos plugins solo necesitan notificaciones; otros necesitan metadata de kept/dropped |
| ¿Qué queda sin soporte a propósito? | El usuario no debe asumir equivalencia OpenClaw donde el runtime nativo posee más estado |

El contrato de soporte del runtime Codex está documentado en *Codex harness runtime* (OpenClaw, s. f., https://docs.openclaw.ai/plugins/codex-harness-runtime#v1-support-contract).

Las refs de modelo en config (por ejemplo `agents.defaults.model`) se parsean partiendo en el **primer** `/`. Usa `provider/model` al configurar modelos. Si el ID del modelo mismo contiene `/` (estilo OpenRouter), incluye el prefijo de provider, por ejemplo `openrouter/moonshotai/kimi-k2`. Si omites el provider, OpenClaw prueba un alias primero, luego un match único de provider configurado, y solo entonces cae al provider default configurado (OpenClaw, *Agent runtime*, s. f.).

Los prompts inbound que llegan a mitad de corrida se dirigen a la corrida actual por defecto. El runtime OpenClaw comprueba steering antes de lanzamientos de tool no arrancados y de la siguiente llamada al modelo. Un tool en marcha continua; las llamadas secuenciales no arrancadas se saltan, mientras las paralelas continúan tras cruzar su checkpoint de lanzamiento. Las llamadas saltadas reciben resultados emparejados sintéticos antes de que el modelo vea el steer. `/queue steer` es la conducta default de corrida activa (OpenClaw, *Agent runtime*, s. f.; *Command queue*, s. f., https://docs.openclaw.ai/concepts/queue).

Las filas de sesión del runtime embebido viven en la base SQLite por agente `~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite`. Los archivos JSONL de transcript pueden seguir bajo `~/.openclaw/agents/<agentId>/sessions/` como entradas de migración legacy. La historia activa se guarda en SQLite. El session ID es estable y lo elige OpenClaw. OpenClaw no lee carpetas de sesión de otras tools (OpenClaw, *Agent runtime*, s. f.).

**Caso.** La config aun tiene un pin de agente entero `agents.defaults.agentRuntime` de una release vieja. La selección de runtime lo ignora. Status muestra un loop `openclaw` o `codex` inesperado hasta que inspeccionas la política de alcance de modelo y corres `openclaw doctor --fix` (OpenClaw, *Agent runtimes*, s. f.).

Cita *Agent runtimes* para capas, superficies Codex, orden de selección y pins de agente entero ignorados. Cita *Agent runtime* para el workspace embebido y el checkpoint de steer. Cita *ACP agents* para spawn. Cita *ACP* para modo bridge. Cita Hermes *Agent Loop Internals* solo en el párrafo de compara.

Los alias de CLI backend difieren de los ids de harness embebido. `claude-cli` es un CLI backend. `codex` es un harness de plugin embebido. `acp` es un runtime de spawn, no un `agentRuntime.id` que pones en `openai/*`. Mezclar esos tres identificadores es el misconfig habitual.

El setup común de suscripción ChatGPT/Codex usa OAuth Codex para auth, pero mantiene la ref de modelo como `openai/*` y selecciona el runtime `codex`. Eso no significa "usa facturación API", y no significa que el canal, el catálogo de provider o el session store de OpenClaw se vuelvan Codex (OpenClaw, *Agent runtimes*, s. f.).

Si `openclaw doctor` avisa que el plugin `codex` está habilitado mientras refs de modelo Codex legacy permanecen en config, trátalo como estado de ruta legacy y corre `openclaw doctor --fix` para reescribirlo a `openai/*` con el runtime Codex.

Como mínimo, fija `agents.defaults.workspace` y recomienda con fuerza `channels.whatsapp.allowFrom` (OpenClaw, *Agent runtime*, s. f.). La política de runtime pertenece a rutas de provider/model, no a las claves ignoradas de runtime de agente entero.

Esta lección se detiene en familias de runtime, el split de nombre Codex, el orden de selección y la horquilla ACP frente a nativo. Los archivos de workspace, las sesiones y el spawn ACP viven en lecciones posteriores.

## Caso — el runtime que no era el que creían

Un equipo configuró un runtime de Codex y esperaba el loop embebido. El log mostraba otro runtime. La lección: el loop embebido es el default y el ownership de runtime decide quién controla el bucle. Confundir las dos familias de runtime es cómo se depura la capa equivocada.
