## VRAM en este modelo: QLoRA a 24GB

Los números de la guía de train para **Qwen3.8-27B**, que *no* son la tabla genérica de mínimos:

- **<Term id="qlora">QLoRA</Term> funciona con 24GB.**
- **<Term id="lora">LoRA</Term> necesita más de 36GB.**
- **<Term id="full-ft">El ajuste completo</Term> usa 4× más VRAM.**

Empieza en 4-bit desde [`unsloth/Qwen3.8-27B-unsloth-bnb-4bit`](https://huggingface.co/unsloth/Qwen3.8-27B-unsloth-bnb-4bit). Después del entrenamiento **exportas** a NVFP4, FP8, GGUF y compañía. Entrenar en 4-bit no es el mismo objeto que servir en 4-bit; el adapter es pequeño en ambos casos.

La tabla genérica de requisitos listaba QLoRA 27B a 22GB mínimo. Esta página dice que 24GB funciona. Cree a la **página del modelo** para esta arquitectura, y aun así trata 24GB como un presupuesto que puedes reventar con contexto, visión y batch.

## Conservar el razonamiento, o olvidarás cómo pensar

Qwen3.8 es un modelo de **thinking híbrido**. Si quieres **conservar la capacidad de razonar**, la regla de la guía de train es precisa: mezcla **ejemplos con estilo de razonamiento** con **respuestas directas**, y mantén **al menos un 75% de datos de razonamiento**.

¿Por qué 75%, y no "unas trazas de adorno"? El SFT sobre respuestas directas cortas es **<Term id="catastrophic-forgetting">olvido catastrófico</Term>** de la traza de think. El modelo sigue completando. Deja de *mostrar el trabajo* que pagaste al elegir un checkpoint thinking. Las filas de respuesta directa enseñan "sáltate el bloque, emite la etiqueta". Si esas filas dominan, el token de think se vuelve raro en la distribución de entrenamiento, y al servir los controles híbridos no tienen nada sobre lo que condicionar.

La mezcla es una decisión de datos, no de rango. Subir `r` no restaurará trazas que nunca mostraste. Después de la corrida, evalúa en prompts que **necesiten** una traza — herramientas de varios pasos, demostraciones, políticas largas — no solo en FAQs de una línea.

**Case.** Un equipo hace fine-tune solo con respuestas directas cortas: FAQs de una línea, sin trazas. La pérdida se ve sana. Al servir, el modelo híbrido deja de pensar. El arreglo es la mezcla: **al menos 75% con estilo de razonamiento**, el resto puede ser directo. Después evalúa en prompts que de verdad exijan una traza.

## Datos: una columna `text`, ya en la plantilla Qwen

La receta SFT quiere JSONL cuyas filas ya tienen un campo **`text`**, renderizado con la **plantilla de chat Qwen**. No entregues al entrenador `messages` crudos y esperes. Aplica primero `tokenizer.apply_chat_template`. La misma plantilla que servirás. **El mismo EOS.**

Forma de un JSONL de un ejemplo. El valor de `text` es lo que produjo `apply_chat_template` — no inventes un segundo dialecto:

```json
{"text": "<the exact string tokenizer.apply_chat_template produced for one conversation>"}
```

Cómo se produce esa cadena:

```python
messages = [
    {"role": "user", "content": "Reset the warehouse printer."},
    {"role": "assistant", "content": "<think>\nNeed the official power-cycle steps, then a status check.\n</think>\nPower off. Wait ten seconds. Power on. Confirm idle."},
]
text = tokenizer.apply_chat_template(
    messages,
    tokenize=False,
    add_generation_prompt=False,
)
```

`dataset_text_field="text"` en `SFTConfig` es cómo TRL encuentra esa columna. Si tu archivo usa `prompt` o `output`, el entrenador no verá la conversación renderizada salvo que renombres. `add_generation_prompt=False` porque estas filas son turnos **completados**.

## Receta SFT de texto, cada flag

Esta es la receta mínima oficial de la [guía de train](https://unsloth.ai/docs/models/qwen3.8/train). Los hiperparámetros coinciden con esa página. Vuelve a leerla el día que corras; los flags se mueven.

```python
from unsloth import FastModel
from datasets import load_dataset
from trl import SFTTrainer, SFTConfig

max_seq_length = 2048

dataset = load_dataset(
    "json",
    data_files = "train.jsonl",
    split = "train",
)

model, tokenizer = FastModel.from_pretrained(
    model_name = "unsloth/Qwen3.8-27B-unsloth-bnb-4bit",
    max_seq_length = max_seq_length,
    load_in_4bit = True,
    full_finetuning = False,
    offload_embedding = True,
)

model = FastModel.get_peft_model(
    model,
    finetune_vision_layers     = False,
    finetune_language_layers   = True,
    finetune_attention_modules = True,
    finetune_mlp_modules       = True,
    r = 16,
    lora_alpha = 16,
    lora_dropout = 0,
    bias = "none",
    use_gradient_checkpointing = "unsloth",
    random_state = 3407,
    use_rslora = False,
    loftq_config = None,
)

trainer = SFTTrainer(
    model = model,
    tokenizer = tokenizer,
    train_dataset = dataset,
    args = SFTConfig(
        dataset_text_field = "text",
        max_seq_length = max_seq_length,
        per_device_train_batch_size = 1,
        gradient_accumulation_steps = 4,
        warmup_steps = 10,
        max_steps = 100,
        learning_rate = 2e-4,
        logging_steps = 1,
        optim = "adamw_8bit",
        output_dir = "outputs_qwen38",
        seed = 3407,
        dataset_num_proc = 1,
        report_to = "none",
    ),
)

trainer.train()
```

Léela como lista de comprobación, no como papel pintado.

**`FastModel`, no `FastLanguageModel`.** Qwen3.8 es un VLM en arquitectura `qwen3_5`. La página de train importa `FastModel`.

**`max_seq_length = 2048`.** Un contexto de corrida de humo. Los 262k de la ficha son un número de servicio. En 24GB, 2048 es el arranque documentado. Súbelo solo después de que una corrida corta termine.

**`load_dataset("json", data_files="train.jsonl", split="train")`.** JSONL local. El nombre de split `train` es el que Hugging Face Datasets usa para un solo archivo sin splits internos.

**`model_name="unsloth/Qwen3.8-27B-unsloth-bnb-4bit"`.** Quant dynamic 4-bit de Unsloth, la base QLoRA. No es un GGUF. No es el original 16-bit salvo que tengas la VRAM.

**`load_in_4bit=True`, `full_finetuning=False`.** QLoRA. Solo un método verdadero a la vez.

**`offload_embedding=True`.** Opcional. Aparca el **embedding de entrada no atado**, grande, en RAM para que **baje la VRAM residente**. Unsloth **lo desactiva solo en plataformas no soportadas**. Déjalo encendido en NVIDIA 24GB salvo que el loader lo apague.

**`finetune_vision_layers=False`.** Este dataset es texto. No quieres que el encoder de visión se desvíe en filas que nunca muestran un píxel. Lenguaje, atención y MLP se quedan en **True** para que LoRA pegue en el mezclador y en el feed-forward, que es cómo Unsloth (citando QLoRA) iguala la calidad del ajuste completo.

**`r=16`, `lora_alpha=16`.** Rango 16 es el arranque documentado — capacidad sin un pico de memoria. Alpha igual al rango, así `alpha / rank = 1`, la línea base oficial. Dropout **0** porque Unsloth optimiza ese camino. `bias="none"` para entrenar más rápido y con menos memoria; entrenar términos de sesgo añade parámetros casi sin ganancia.

**`use_gradient_checkpointing="unsloth"`.** Su checkpointing, no un `True` genérico. Holgura extra de VRAM; consérvalo cuando hay OOM.

**`random_state=3407` y `seed=3407`.** Reproducibilidad. Los notebooks de Unsloth usan esta semilla para que tu corrida de humo sea comparable a la suya.

**`use_rslora=False`, `loftq_config=None`.** LoRA estabilizado por rango y LoftQ son avanzados. LoftQ puede disparar la memoria al arrancar. Déjalos apagados en la primera corrida.

**`dataset_text_field="text"`.** El nombre de la columna. Si no coincide con la clave del JSONL, estás entrenando sobre nada útil.

**`per_device_train_batch_size=1`, `gradient_accumulation_steps=4`.** Batch efectivo 4. Batch 1 es el suelo de VRAM. Accum 4 mantiene estables las actualizaciones. Unsloth hizo equivalentes batch y accum tras su arreglo de acumulación de gradiente.

**`warmup_steps=10`, `max_steps=100`, `learning_rate=2e-4`.** Warmup de diez pasos en una corrida de **humo** de 100. `2e-4` es el valor por defecto de LoRA/QLoRA. **`max_steps=100` no es un producto.** Sustitúyelo por `num_train_epochs` en 1–3 cuando los datos sean reales.

**`logging_steps=1`.** Para ver moverse la pérdida. La instrucción de Studio es la misma: la pérdida debe bajar de forma constante.

**`optim="adamw_8bit"`.** AdamW de 8-bit, para que el estado del optimizador no cancele el ahorro del 4-bit.

**`output_dir="outputs_qwen38"`.** Checkpoints locales. Cámbialo. No compartas directorio con otra corrida.

**`dataset_num_proc=1`.** Un proceso para mapear/tokenizar. Más seguro en Kaggle y en máquinas pequeñas; trabajadores extra pueden hacer OOM de la RAM del host durante el map.

**`report_to="none"`.** Sin wandb salvo que te hayas apuntado.

Si hay OOM: **reduce `max_seq_length`**, mantén **batch size 1**, mantén el checkpointing `"unsloth"`. Esa es la tríada oficial. No "subas el batch" en una T4.

<Steps>
1. Renderiza el JSONL con la plantilla de chat Qwen en una columna `text`. Conserva al menos un 75% de filas con estilo de razonamiento si necesitas trazas al servir.
2. Carga `unsloth/Qwen3.8-27B-unsloth-bnb-4bit` en 4-bit, `full_finetuning=False`, `offload_embedding=True`.
3. Engancha LoRA con checkpointing Unsloth. Capas de visión **apagadas** para texto. `r=16`, `lora_alpha=16`.
4. Entrena con el `SFTConfig` de arriba. Si hay OOM, recorta `max_seq_length`, deja batch 1.
5. Evalúa en prompts reservados que aún necesiten una traza de razonamiento. Después exporta con la misma plantilla y el mismo EOS.
</Steps>

## RL: camino `qwen3_5`, y `fast_inference=False`

El aprendizaje por refuerzo usa el mismo id de arquitectura, así que sigues el **camino RL Unsloth de Qwen3.5**. Desactiva la inferencia vLLM rápida. La página de train imprime esta carga:

```python
from unsloth import FastModel

model, tokenizer = FastModel.from_pretrained(
    model_name = "unsloth/Qwen3.8-27B-unsloth-bnb-4bit",
    max_seq_length = 2048,
    load_in_4bit = True,
    fast_inference = False,
)
```

**¿Por qué `fast_inference=False`?** La guía RL de Unsloth es explícita para arquitecturas cuyos kernels vLLM no están listos: pon `fast_inference=False` al cargar, como documentan para Qwen3.5 y para "RL en modelos no soportados". Qwen3.8 comparte `qwen3_5`. Los kernels vLLM rápidos **no** son el camino de entrenamiento para esta arquitectura todavía. La instrucción oficial es apagar ese flag, no "activar vLLM para ir más rápido" en este modelo.

Enlaza esto con la [guía RL de Unsloth](https://unsloth.ai/docs/get-started/reinforcement-learning-rl-guide). **GRPO** (Group Relative Policy Optimization) muestrea **G** respuestas por pregunta, las puntúa con una **recompensa verificable**, y convierte esas recompensas en ventajas por **Z-score**. **No hay modelo de valor** ni modelo de recompensa aprendido al estilo PPO — por eso GRPO cabe en una GPU. RLVR significa que la recompensa se puede comprobar (mates, código, una rúbrica de chequeos pequeños), no una intuición.

La paciencia es el método. Unsloth te dice que esperes **cientos de pasos** antes de que la recompensa suba de verdad; 300 es el número que escriben como mínimo, y a veces son 1000. Parte de un checkpoint **Instruct**, no de un base, si la probabilidad de una muestra correcta es ~0 — si esa probabilidad es siempre cero, RL nunca ve un rollout bueno. Usa recompensas **verificables**. Para Qwen3.8, el camino gratis es el [notebook GRPO Kaggle de Muse Glimmer 30B](https://github.com/unslothai/notebooks/blob/main/nb/Kaggle-Muse_Glimmer_(30B)-Conversational.ipynbB)-GRPO.ipynb&accelerator=nvidiaTeslaT4) con el **id de modelo cambiado a Qwen3.8**. Unsloth dice que RL también funciona en **24GB**. No pegues ese notebook en esta lección; cambia el id del modelo y conserva su entrenador.

La tasa de aprendizaje GRPO en la guía de hiperparámetros arranca cerca de **`5e-6`**, no `2e-4`. Si reutilizas la de SFT en GRPO, no estás siguiendo la página de RL.

## Caso — GRPO sobre Qwen3.8 y la recompensa que nunca llegó

Un equipo monta RL GRPO sobre Qwen3.8-27B Instruct con un dataset propio de mates. Primer run con `max_steps=300`. A los 200 steps la recompensa promedio sigue clavada en 0.0. Piden ayuda al foro; les dicen "espera más". Suben a `max_steps=1000` y reentrenan. A los 800 steps sigue en 0.0 con varianza casi cero. Sospechan bug del trainer. Diagnóstico real: la guía RL de Unsloth es explícita — GRPO muestrea **G** respuestas por pregunta, las puntúa con una **recompensa verificable** y construye ventajas con Z-score. Si la probabilidad de una respuesta correcta bajo el checkpoint **Instruct** ya es ~0, **nunca verás un rollout bueno** y la línea base se queda en 0. Su dataset mezclaba respuestas numéricas y preguntas de respuesta libre; el reward parser solo reconocía el formato numérico, así que la mayoría de rollouts caían en reward=0 con varianza nula. Tres arreglos. Primero, empezar desde un checkpoint Instruct, no desde un Base — la receta lo asume y no lo repite. Segundo, depurar el reward con `print(reward_fn(question, sample))` sobre 20 ejemplos a mano, no con GRPO. Tercero, recortar el dataset a lo que el reward sabe puntuar, no añadir más volumen para "ver si sube". Con esas tres, la recompensa empezó a moverse a los 250 steps. Lección: GRPO sin recompensa verificable, o con reward que no parsea, es teatro caro.
