## Tres controles, tres respuestas

La fuente primaria es [*Sandbox vs tool policy vs elevated*](https://docs.openclaw.ai/gateway/sandbox-vs-tool-policy-vs-elevated) de OpenClaw (s. f.). OpenClaw tiene tres controles relacionados pero distintos:

1. **Sandbox** (`agents.defaults.sandbox.*`, `agents.entries.*.sandbox.*`, o una política required de creator-role) decide **donde corren las tools** (backend sandbox vs host).
2. **Tool policy** (`tools.*`, `tools.sandbox.tools.*`, `agents.entries.*.tools.*`) decide **que tools están disponibles**.
3. **Elevated** (`tools.elevated.*`) es un **escape hatch solo-exec** del sandboxing ordinario (`gateway` por defecto, o `node` cuando el target exec es `node`). No puede bypasear un sandbox required de un creator role.

La lección genérica [tools](/es/m/tools) permanece agnóstica del harness. Esta es la jaula de tres capas de OpenClaw.

```bash
openclaw sandbox explain
openclaw sandbox explain --session agent:main:main
openclaw sandbox explain --agent work
openclaw sandbox explain --json
```

El inspector imprime modo/scope/workspace access efectivo de sandbox, si la sesión esta sandboxed ahora (main vs non-main), allow/deny efectivo de tools de sandbox (y si vino de agente/global/default), gates elevated, y key paths de fix-it (OpenClaw, *Sandbox vs tool policy vs elevated*, s. f.).

## Sandbox: donde corren las tools

`agents.defaults.sandbox.mode`:

- `"off"`: las sesiones corren en el host salvo que el operator role del creator exija sandboxing.
- `"non-main"`: solo las sesiones non-main están sandboxed (sorpresa común para grupos/canales).
- `"all"`: todo esta sandboxed.

`agents.defaults.sandbox.workspaceAccess` controla que puede ver el sandbox: `"none"`, `"ro"` o `"rw"`.

Un operator role con `sandbox: "required"` sobreescribe el modo de agente, no se escapa por ejecución elevated ni host overrides, y falla cerrado cuando su sandbox no puede provisionarse. Citen *Named operator roles* (OpenClaw, s. f., https://docs.openclaw.ai/gateway/operator-scopes#named-operator-roles).

El workspace es el cwd default, no un sandbox duro. Los paths absolutos pueden seguir alcanzando el resto del host salvo que sandboxing este habilitado. Citen *Agent workspace* (OpenClaw, s. f., https://docs.openclaw.ai/concepts/agent-workspace) y *Sandboxing* (OpenClaw, s. f., https://docs.openclaw.ai/gateway/sandboxing).

Cuando sandboxing está habilitado y `workspaceAccess` no es `"rw"`, las tools operan dentro de un workspace sandbox bajo `~/.openclaw/sandboxes`, no el workspace del host.

Los bind mounts perforan el filesystem del sandbox. El default es read-write si omites el modo; prefieran `:ro` para source/secrets. `scope: "shared"` ignora binds per-agente. Bindear `/var/run/docker.sock` entrega control del host al sandbox. OpenClaw valida fuentes de bind dos veces, incluida tras resolver por el ancestro existente más profundo, así que escapes de parent symlink no bypasean cheques de path bloqueado.

## Tool policy: que tools existen

Dos capas importan: perfil de tools (`tools.profile`) más allow/deny global/per-agente, y **sandbox tool policy** que solo aplica cuando esta sandboxed (`tools.sandbox.tools.allow`/`deny`).

Reglas de pulgar de la página (OpenClaw, *Sandbox vs tool policy vs elevated*, s. f.):

- `deny` siempre gana.
- Si `allow` no está vacío, todo lo demás se trata como bloqueado.
- La política de tools es el hard stop: `/exec` no puede sobreescribir una tool `exec` denegada.
- La política filtra por nombre; no inspecciona efectos secundarios dentro de `exec`. Si `exec` está permitido, denegar `write` no hace los commands de shell de solo lectura.
- `/exec` solo cambia defaults de sesión para senders autorizados; no otorga acceso a tools.

Los logs del Gateway incluyen entradas de audit `agents/tool-policy` cuando un paso de política quita tools o una política de sandbox bloquea una llamada.

<Callout>
Las sesiones ACP hoy corren en el runtime del host, **no** dentro del sandbox de OpenClaw. Los requesters sandboxed no pueden lanzar ACP. Elevated tampoco envuelve ACP. Usen `runtime: "subagent"` para trabajo delegado con sandbox (OpenClaw, *ACP agents*, s. f., https://docs.openclaw.ai/tools/acp-agents).
</Callout>

## Grupos dentro de la política de sandbox

La política de tools de sandbox soporta shorthands `group:*`. Copien la tabla de la página de comparación que están enseñando; la página config-tools lista un `group:ui` ligeramente distinto (OpenClaw, *Sandbox vs tool policy vs elevated*, s. f.).

Para agentes read-only, denieguen `group:runtime` además de tools de filesystem mutantes salvo que la política de filesystem del sandbox ya fuerce read-only.

Para servidores MCP sandboxed, la política de tools de sandbox es un segundo gate de allow. Añadan `bundle-mcp`, `group:plugins` o un glob de servidor a `tools.sandbox.tools.alsoAllow`. `openclaw doctor` revisa esta forma para `mcp.servers` gestionados por OpenClaw.

## Elevated: solo-exec

Elevated **no** otorga tools extra; solo afecta `exec`.

- Si están sandboxed de forma ordinaria, `/elevated on` (o `exec` con `elevated: true`) corre fuera del sandbox (las approvals pueden seguir aplicando). Los sandboxes required de creator-role rechazan ejecución elevated.
- `/elevated full` salta exec approvals para la sesión.
- Si ya corren direct, elevated es efectivamente un no-op (sigue gated).
- Elevated no esta scoped a skills y no sobreescribe allow/deny de tools.
- Elevated no otorga overrides arbitrarios cross-host desde `host=auto`; sigue las reglas normales de target exec y solo conserva `node` cuando el target configurado/sesión ya es `node`.

Gates: `tools.elevated.enabled` y allowlists de sender `tools.elevated.allowFrom.<channel>`. Elevated per-agente solo puede restringir más. Citen *Elevated Mode* (OpenClaw, s. f., https://docs.openclaw.ai/tools/elevated).

**Caso.** Un grupo Slack esta sandboxed porque el modo es `non-main`. El operador penso "este es mi bot, así que es main." Las claves de grupo nunca son `agent:<id>:main`. Usen `sandbox explain` y lean la session key, o cambien el modo a `off` si esa es la intención (OpenClaw, *Sandbox vs tool policy vs elevated*, s. f.).

**Caso.** `exec` está denegado por tool policy. `/elevated on` no hace nada útil. Elevated no puede restaurar una tool denegada (OpenClaw, *Sandbox vs tool policy vs elevated*, s. f.).

## Comparar, sin mezclar knobs

El sandboxing de Hermes, cuando existe, es un asunto del loop Hermes (Nous Research, *Agent Loop Internals*, s. f., https://hermes-agent.nousresearch.com/docs/developer-guide/agent-loop). El sandbox de OpenClaw son backends provisionados por el Gateway más una capa separada de tool-policy más un hatch elevated solo-exec. No peguen un flag Docker en `tools.deny`. Citen la página de comparación para que clave cambiar.

Fixes comunes de jaula: deshabilitar sandboxing ordinario con `agents.defaults.sandbox.mode=off` (no sobreescribe un sandbox required de creator role); o permitir la tool dentro del sandbox quitandola del deny de sandbox o anadiendola al allow de sandbox. Chequen `openclaw logs` por la entrada `agents/tool-policy`.

Clamp de sandbox en session tools: cuando la sesión actual esta sandboxed y `agents.defaults.sandbox.sessionToolsVisibility` es `"spawned"` (default), el acceso se queda limitado a sesiones spawned incluso si visibility es `"all"`. Citen *Tools and custom providers* (OpenClaw, s. f., https://docs.openclaw.ai/gateway/config-tools).

Browser `target: "host"` desde una sesión sandboxed exige `agents.defaults.sandbox.browser.allowHostControl=true`. Eso no está implicado por `tools.alsoAllow: ["browser"]`.

La sección `AGENTS.md` `## Tools` del workspace no controla que tools existen. La política si.

Esta lección se detiene en las tres capas, la sorpresa `non-main`, deny-gana, elevated-es-solo-exec, y `sandbox explain`. Compaction y cron no cambian la jaula.

La particularidad: "bloqueado" no es un solo knob. Pregunten donde, cual tool, o exec-en-host, luego elijan sandbox, policy o elevated.

Las claves de tools de proveedor aceptan provider (por ejemplo anthropic) o provider/model. El orden es perfil base, luego perfil de proveedor, luego allow/deny. Un perfil de proveedor minimal sobre un perfil global coding es como un modelo barato pierde exec sin cambiar el default del agente.

docker.binds es un cheque rápido de seguridad, no un mount de conveniencia. Los paths hoja inexistentes se chequean igual con seguridad. Si un bind resuelve por un parent symlink a un path bloqueado o fuera de allowed roots, el bind se rechaza.

Workspace access es independiente de los modos de bind. Pueden tener workspaceAccess none y aun perforar vía un bind rw si configuraron uno. Lean ambos knobs.

ACP, payloads command de cron, y elevated son tres historias distintas del lado host. Los payloads command exigen operator.admin y corren dentro del scheduler del Gateway; no son tools.exec. Elevated es exec gated por sesión fuera del sandbox. ACP es un proceso de harness externo. Citen cada página; no los fusionen en "unsandboxed significa root."

## Caso — el comando que escapó del sandbox

Un agente pidió ejecutar un comando con write y el sandbox lo denegó. La política de tools no lo permitía. La lección: sandbox, tool policy y elevated son tres controles con tres respuestas. Deny siempre gana; elevated no restaura una tool denegada.
